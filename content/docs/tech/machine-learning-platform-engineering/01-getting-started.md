모델을 한 번 잘 학습시키는 일과 그 모델을 서비스로 계속 운영하는 일은 다른 문제다. 1장은 그 차이를 ML 생애주기와 플랫폼의 역할로 설명한다. 운영 중인 모델에 문제가 생겼을 때 그 모델을 만든 데이터와 코드, 설정까지 거슬러 올라갈 수 있어야 고칠 곳을 찾을 수 있다.

## ML 생애주기는 앞 단계로 자주 되돌아간다

ML 생애주기는 문제 정의, 데이터 수집과 준비, 학습, 평가, 배포, 개선을 잇는 지도다. 직선으로 그려도 실제로는 순환한다. 지표가 나쁘면 모델만 바꾸지 않고 데이터와 문제 정의도 다시 본다.

학습은 데이터와 정답으로 모델의 가중치를 구하는 과정이고, 추론은 학습이 끝난 모델에 새 입력을 넣어 예측을 얻는 과정이다. 신분증 탐지라면 사진이 입력이고 카드 위치를 표시한 경계 상자와 클래스가 정답이다. 요청이 올 때마다 모델을 다시 학습하지는 않는다.

평가(evaluation)는 학습에 쓰지 않은 데이터로 성능을 재는 일이고, 책이 말하는 모델 검증(validation)은 업무 목적에 맞는지 확인하는 일에 가깝다. 학습, 검증, 테스트로 나눌 때의 검증셋은 모델과 설정을 고르는 데이터라서 같은 단어라도 뜻이 다르다. 테스트셋은 선택에 쓰지 않고 마지막 확인용으로 남긴다.

## 운영에서는 재현과 되돌리기가 문제가 된다

실험은 어떤 방법이 좋은지를 찾고, 운영은 그 방법을 안전하게 반복하고 바꿀 수 있는지를 묻는다.

| 실험에서 묻는 질문 | 운영에서 추가되는 질문 |
| --- | --- |
| 어떤 데이터와 모델이 효과적인가? | 그 데이터, 코드, 설정을 다시 찾을 수 있는가? |
| 평가 점수가 충분한가? | 실제 입력에서도 품질과 응답 시간이 유지되는가? |
| 학습을 실행할 수 있는가? | 실패를 감지하고 재실행하거나 되돌릴 수 있는가? |

같은 코드라도 데이터가 바뀌면 다른 모델이 나온다. 계보(lineage)는 모델에서 데이터, 코드, 설정, 실행 기록까지 거슬러 올라가는 연결이다. 가중치 파일만 보관해서는 결과가 나쁜 이유를 설명할 수 없다.

배포 단위에는 가중치 외에 전처리와 응답을 만드는 코드도 들어간다. 학습 때는 이미지를 리사이즈하고 정규화했는데 API가 원본을 그대로 넣으면 같은 모델도 다른 입력을 받는다. 이것이 학습과 서빙의 불일치다. 문제가 생겨 되돌릴 때도 모델과 호환되는 전처리, 서비스 코드를 함께 되돌려야 한다.

재학습은 새 후보를 만드는 과정이고 출시는 그 후보를 사용자에게 연결하는 결정이다. 점수가 좋아도 특정 문서 유형에서 실패하거나 지연이 늘면 출시를 보류할 수 있다. 재학습을 자동화하는 것과 결과를 무조건 자동 출시하는 것은 다른 문제다. 그래서 배포 전에 되돌아갈 모델, 코드, 설정 조합과 승인, 복구를 맡을 사람을 정해 둔다.

## 출시 조합은 모델 버전보다 넓다

출시를 설명하려면 모델 버전 하나로는 부족하다. 학습 코드 커밋, 데이터 스냅샷, 분할 규칙, 전처리 버전, 모델 참조, 서빙 이미지, 평가 보고서, 되돌아갈 이전 출시를 한 묶음으로 기록해야 한다. 모델이 그대로여도 좌표 복원 코드를 바꾸면 새 출시가 된다.

데이터 스냅샷 자리에 지금도 내용이 바뀌는 폴더 이름을 적으면 재현 정보로 부족하다. 아래 코드는 같은 파일 이름에서 내용만 바뀌었을 때 해시가 달라지는 것을 확인한다.

```python
import hashlib
import json
from pathlib import Path

snapshot = Path("lineage_snapshot.csv")
if snapshot.exists():
    raise FileExistsError("Use an empty study folder to preserve existing data")
snapshot.write_text("image,label\ncard-001,card\n", encoding="utf-8")
original = hashlib.sha256(snapshot.read_bytes()).hexdigest()
manifest = {"dataset": snapshot.name, "sha256": original}
Path("lineage_manifest.json").write_text(
    json.dumps(manifest, indent=2), encoding="utf-8"
)
print("Recorded dataset:", manifest["dataset"])
print("Original SHA-256:", original)
print("Matches before change:", hashlib.sha256(snapshot.read_bytes()).hexdigest() == original)
with snapshot.open("a", encoding="utf-8") as stream:
    stream.write("card-002,no-card\n")
current = hashlib.sha256(snapshot.read_bytes()).hexdigest()
print("Modified SHA-256:", current)
print("Matches after change:", current == original)
```

행 하나를 추가하자 비교 결과가 `True`에서 `False`로 바뀌었다. **파일의 위치와 내용의 버전은 다르다.** 해시는 내용을 복구해 주지 않으므로 원본 스냅샷도 보존해야 하고, 이런 기록이 있어도 난수나 라이브러리, 하드웨어 차이까지 같은 숫자로 재현된다는 보장은 없다.

## ML 엔지니어는 원인을 여러 층에서 좁힌다

책이 그리는 ML 엔지니어는 알고리즘 하나보다 소프트웨어 설계와 테스트, 데이터 처리, 모델 평가, 실행 환경과 자동화를 엮어 다루는 사람이다. 모델이 카드를 잘 찾지 못한다는 증상 하나에도 전처리에서 회전 정보를 빠뜨렸을 수 있고, 새 카메라의 촬영 조건이 학습 데이터와 다를 수 있고, 모델 로딩에 실패해 다른 버전이 돌고 있을 수도 있다. 코드 버그, 데이터 오류, 모델의 한계, 인프라 장애 중 어디인지부터 좁혀야 한다.

한 사람이 모든 영역의 전문가일 필요는 없다. 데이터와 평가를 아는 사람과 서비스와 인프라를 아는 사람이 같은 실행 흐름을 보면서 책임과 연결 지점을 합의하는 일이 먼저다. 책은 Python과 기본적인 ML 흐름을 안다고 가정하고, Kubernetes 기초부터 플랫폼을 하나씩 붙여 나간다.

## 플랫폼은 반복을 위한 공통 기반이다

ML 플랫폼은 실험, 학습, 배포, 관측을 반복하게 해 주는 공통 기반이다. 화면에 도구를 모아 놓는다고 플랫폼이 되지는 않는다. 원천 데이터 수집이나 웨어하우스 전체까지 책임질 필요는 없고, 무엇을 받아 무엇을 제공하며 누가 운영하는지부터 정한다.

![업무 요구사항에서 데이터 준비와 모델 학습 및 평가를 거쳐 API 배포와 모니터링으로 이어지는 ML 플랫폼 구성. 피처 스토어, 실험 추적, 모델 레지스트리가 각 단계를 연결한다.](/images/ml-platform-engineering/figure-1-04.png?v=2)

그림 1.4. ML 플랫폼의 구성. 출처: Machine Learning Platform Engineering, 1장.

그림에서 파이프라인 오케스트레이션은 준비, 학습, 평가, 배포의 순서와 의존성을 관리한다. 실험 추적은 어떤 조건에서 어떤 결과가 나왔는지 남기고, 모델 레지스트리는 그중 관리하고 서비스할 모델 버전을 정한다. 피처 스토어의 선이 학습과 API 양쪽으로 이어지는 것은 학습 때 계산한 특성을 요청 시점에도 같은 의미로 제공한다는 뜻이다. 책은 이 역할을 Kubeflow Pipelines, MLflow, Feast, 컨테이너와 CI/CD로 채운다.

도구를 설치한다고 문제가 풀리지는 않는다. MLflow가 데이터 품질을 보장하지 않고, 피처 스토어가 학습과 서빙의 모든 차이를 없애지도 않는다. 관리형 서비스는 구축 부담을 줄이지만 통합, 권한, 비용 관리가 남고, 자체 구축은 조정이 자유로운 대신 업그레이드와 장애 대응을 떠안는다. 총비용은 같은 요구사항과 기간을 놓고 비교한다.

LLM 애플리케이션에서도 버전, 배포, 모니터링은 그대로 필요하다. 여기에 문서와 인덱스, 프롬프트, 답변 평가, 토큰 비용이 추적 대상으로 더해진다. 1장은 이 확장을 예고만 하고 구현은 후반부에서 다룬다.

## 세 프로젝트는 같은 생애주기를 반복한다

책은 신분증 객체 탐지, 영화 추천, 문서 기반 RAG 챗봇(DakkaBot)을 만든다. 데이터와 모델은 달라도 준비, 학습, 검증, 배포, 관측, 개선이라는 문제를 공유한다.

| 프로젝트 | 하는 일 | 비교할 운영 문제 |
| --- | --- | --- |
| 신분증 탐지 | 이미지에서 카드 위치 탐지 | 라벨, 좌표, 촬영 단위 분할 |
| 영화 추천 | 평점으로 추천 | 시점, 식별자, 새 사용자 |
| DakkaBot | 사내 문서를 검색해 답변 | 문서 최신성, 권한, 근거, 토큰 비용 |

카드 탐지만 봐도 운영 문제가 모델 밖에 많다. API는 왼쪽 위와 오른쪽 아래 픽셀 좌표를 돌려주는데 YOLO 라벨은 정규화한 중심 좌표와 폭, 높이를 쓴다. 이 차이를 잘못 해석하면 모델을 바꾸지 않아도 잘못된 크롭이 나온다. 같은 영상에서 뽑은 비슷한 프레임이 학습셋과 테스트셋에 섞이면 새 촬영 환경에서의 성능을 과대평가하므로 촬영 세션 단위로 나눠야 한다. 재촬영 비율이 줄어도 잘못 자른 사진이 다음 단계로 넘어간다면 성공이라 하기 어려우니, 업무 기준선과 실패 유형을 학습 전에 정해 둔다.

## 정리

모델 파일 하나로는 운영을 설명할 수 없다. 데이터, 코드, 전처리, 평가를 묶은 출시 조합이 있어야 어떤 모델이 왜 배포됐는지 답할 수 있다. 1장은 이 반복을 플랫폼이 떠받친다는 그림만 보여 주고, 2장은 그 반복을 어디까지 자동화할지를 성숙도로 나눈다.
