가전제품마다 플러그 모양이 다르면 연결할 때마다 변환기가 필요합니다. MCP는 도구를 제공하는 서버와 사용하는 앱 사이에 공통 연결 규칙을 둡니다. 다만 콘센트 규격이 같다고 모든 기기를 마음대로 켜도 되는 것은 아닙니다. 연결 규약과 실행 권한은 나눠야 합니다.

이번에는 작은 서버를 별도 프로세스로 띄워 **도구 발견·입력 스키마·정상 호출·오류 반환**을 직접 확인했습니다.

## 13.1 MCP 서버

### 13.1.1 연결이 많아질 때의 문제

날씨, 검색, 문서 저장소와 업무 API마다 호출 방식과 응답 규격이 다릅니다. 모델에 제공할 도구 스키마와 실제 API의 인자를 연결하는 코드도 필요합니다.

같은 서비스가 여러 에이전트에 사용되면 변환과 오류 처리를 각 애플리케이션에서 반복하게 됩니다. API가 바뀌면 여러 래퍼를 함께 수정해야 합니다.

### 13.1.2 Model Context Protocol

MCP는 도구와 자료를 제공하는 쪽과 소비하는 쪽 사이에 공통 인터페이스를 둡니다. MCP를 사용한다고 서비스 고유의 업무 규칙이 사라지는 것은 아닙니다. 연결과 발견, 호출을 공통 규약으로 다룰 수 있게 합니다.

![하나의 AI 애플리케이션인 MCP Host가 여러 Client를 통해 로컬 및 원격 MCP Server에 연결하고, 각 서버는 도구와 원천 자료 또는 API를 제공하는 구조.](/images/ai-agents-and-applications/figure-13-01.png "그림 13.1. MCP Host와 Client, Server의 관계. 출처: AI Agents and Applications, 13장.")

| 구성 요소 | 역할 |
| --- | --- |
| Host | 모델과 사용자 상호작용, 연결과 사용 정책을 관리하는 앱 |
| Client | Host 안에서 특정 서버와 통신하는 구성 요소 |
| Server | 도구, 자료와 프롬프트 등을 규약에 맞게 제공하는 프로그램 |
| 원천 서비스 | 실제 날씨 API나 파일, 데이터베이스 |

Client는 모델 자체가 아닙니다. 서버가 도구를 제공해도 어떤 도구를 사용자에게 허용하고 모델에 노출할지는 Host의 정책입니다. 서버에 접근할 수 있다는 사실과 모든 기능을 실행할 권한이 있다는 사실도 다릅니다.

Tools는 실행 가능한 기능, Resources는 읽을 문맥 자료, Prompts는 재사용 가능한 상호작용 템플릿을 제공하는 개념입니다. 이 장의 실습은 그중 도구 노출에 집중합니다.

### MCP는 REST API를 없애는 것이 아닙니다

외부 업체마다 주문 양식이 달라도 공통 접수 창구를 만들 수 있습니다. 접수 창구 뒤에서는 여전히 업체별 시스템을 호출해야 합니다. MCP 서버도 원천 날씨 서비스의 HTTP API를 감싸는 역할을 할 수 있습니다.

```text
모델의 도구 요청
  → Host가 허용한 도구 실행
  → MCP Client가 규약에 맞게 호출
  → MCP Server가 실제 날씨 API에 요청
  → 원천 응답을 정리해 Client로 반환
  → Host가 도구 결과를 모델에 전달
```

공통화되는 것은 서버와 연결하고 기능을 발견하며 도구를 호출하는 경계입니다. 원천 서비스의 위치 검색, 인증 키, 단위 변환과 오류 해석은 서버 구현에 남습니다. MCP가 LLM과 날씨 사업자 사이의 모든 차이를 자동으로 없애는 것은 아닙니다.

Tools·Resources·Prompts도 모두 “실행 함수”의 다른 이름은 아닙니다. 예를 들어 시간표를 조회하는 도구, 읽을 시간표 문서, 여행 계획을 묻는 프롬프트 양식은 각각 다른 역할입니다. Host가 어떤 기능을 지원하고 어떻게 사용자에게 제공하는지 확인해야 합니다.

### 13.1.3 생태계

MCP SDK와 Inspector, 프레임워크 어댑터를 사용하면 직접 메시지 규약을 구현하는 부담을 줄일 수 있습니다.

서버를 찾는 것과 신뢰하는 것은 다릅니다. 어떤 코드를 실행하고 어떤 외부 주소에 데이터를 보내는지, 노출한 도구가 필요한 권한만 갖는지 확인해야 합니다. 도구 설명과 결과도 무조건 신뢰되는 지시가 아닙니다.

## 13.2 서버 구성 방법

### 13.2.1 문서와 규격

[MCP 공식 아키텍처 문서](https://modelcontextprotocol.io/docs/learn/architecture)는 참여자와 연결 계층, 도구 및 자료의 개념을 설명합니다. 프로토콜은 LLM의 판단 방식이나 에이전트의 업무 정책 전체를 정하지 않습니다.

규격은 버전에 따라 바뀝니다. 책의 예제와 현재 SDK가 사용하는 프로토콜 버전, 초기 연결과 기능 발견 방식이 호환되는지 확인해야 합니다.

### 13.2.2 언어별 SDK

공식 언어별 SDK와 서버 작성에 사용하는 상위 라이브러리는 구분해야 합니다. 책은 FastMCP 계열 도구로 Python 서버를 만듭니다.

같은 이름의 예제를 보더라도 import 경로와 패키지, 지원 버전이 다른지 확인해야 합니다. 라이브러리가 직렬화와 서버 구성을 도와도 외부 API 키와 오류 처리, 권한은 구현의 책임입니다.

### 13.2.3 애플리케이션에서 소비

Host 안의 Client가 서버에 연결해 도구 정의를 얻고, 프레임워크가 사용할 수 있는 도구 형태로 변환합니다. 모델은 그 정의로 요청하고 실행은 연결된 Client를 거쳐 서버에 전달됩니다.

로컬 표준 입출력 연결과 원격 HTTP 연결은 운영 조건이 다릅니다. 원격에서는 인증과 TLS, 시간 제한과 연결 수명, 네트워크 장애를 다뤄야 합니다. 로컬 서버도 Host 권한으로 파일이나 프로세스에 접근할 수 있으므로 검토가 필요합니다.

### 연결부터 호출까지의 수명

전화가 연결됐다고 상대방이 어떤 업무를 처리하는지 아는 것은 아닙니다. MCP에서도 초기화와 기능 발견, 실제 호출을 구분합니다.

| 단계 | 확인하는 것 | 이 단계만으로 알 수 없는 것 |
| --- | --- | --- |
| 전송 연결 | 프로세스 또는 원격 주소와 통신 가능 | 원하는 도구가 있는지 |
| 초기화 | 프로토콜 버전·기능 협상 | 업무 입력으로 정상 처리되는지 |
| 도구 발견 | 이름, 설명, 입력 스키마 | 모델이 그 도구를 잘 고르는지 |
| 도구 호출 | 특정 입력에 대한 실행 결과 | 최종 답변이 결과를 정확히 쓰는지 |
| 연결 종료 | 세션·프로세스 자원 정리 | 외부 작업이 취소됐는지 |

프로토콜의 요청과 응답은 메시지 ID로 연결됩니다. 서버의 업무 결과에도 별도 식별자가 필요할 수 있습니다. 프로토콜 요청 ID, 모델의 tool call ID, 예약 시스템의 예약 번호는 같은 값으로 자동 통일되지 않습니다.

연결을 여는 코드가 종료된 뒤에도 도구를 쓸 계획이라면 수명을 점검해야 합니다. 발견한 도구 정의를 Python 변수로 보관한 것만으로 닫힌 세션이 살아나지는 않습니다. 도구 정의를 가져오는 시점부터 실제 호출이 끝나는 시점까지 연결을 유지하거나, 사용하는 어댑터의 재연결 동작을 명확히 이해해야 합니다.

## 13.3 날씨 MCP 서버

### 13.3.1 구현

모의 날씨를 실제 외부 날씨 API로 바꿉니다. MCP 서버가 장소 입력을 받고 원천 서비스에 질의한 결과를 반환합니다.

장소 이름을 실제 위치 식별자로 해석하는 과정이 필요할 수 있습니다. 같은 이름의 도시와 국가를 구분하고 조회한 위치를 결과에 남겨야 합니다.

API 키는 서버 쪽에 보관하고 모델이나 클라이언트 응답에 노출하지 않습니다. 실제 호출에서는 인증 실패, 요청 제한, 없는 장소와 빈 응답을 구분합니다.

온도 단위와 관측 시간, 현재 날씨인지 예보인지도 응답 계약에 포함해야 합니다. 값만 반환하면 에이전트가 다른 시점의 데이터를 현재 상태로 해석할 수 있습니다.

### 13.3.2 MCP Inspector

Inspector로 서버에 연결하고 도구 목록과 입력 스키마를 확인한 뒤 직접 호출합니다. 이 과정은 LLM의 도구 선택을 제외하고 서버 연결과 실행 자체를 검증합니다.

서버 목록이 보이는 것, 특정 도구 호출이 되는 것, 반환한 데이터가 맞는 것은 서로 다른 확인입니다. 유효한 위치와 잘못된 위치, 원천 서비스 실패를 나눠 시험해야 합니다.

### 13.3.3 테스트 Host

코드에서 Client를 만들고 도구 발견과 호출을 수행합니다. Inspector에서 수동으로 했던 연결을 반복 가능한 테스트로 옮기는 것입니다.

테스트에는 입력과 출력 스키마뿐 아니라 시간 제한과 오류 응답도 포함합니다. 단순 HTTP 200이 업무상 성공을 뜻하지는 않습니다.

### 오류가 어느 경계에서 발생했는지 읽기

| 관찰한 실패 | 경계 | 다른 실패와 구분할 이유 |
| --- | --- | --- |
| Python 실행 파일을 찾지 못함 | 로컬 프로세스 시작 | 도구 구현에 도달하지 못함 |
| 초기화나 메시지 해석 실패 | 프로토콜·전송 | 업무상 “자료 없음”이 아님 |
| 도구 이름 또는 인자 규격 불일치 | 호출 계약 | 클라이언트와 서버의 도구 정의 확인 필요 |
| 없는 장소에 대한 도구 오류 | 업무 처리 | 연결은 정상이어도 요청을 완료하지 못함 |
| 날씨 사업자의 요청 제한 | 원천 서비스 | 서버까지 연결됐지만 외부 의존성이 실패 |

오류를 모두 `null`이나 빈 문장으로 바꾸면 모델은 값이 없는 이유를 모릅니다. 예를 들어 지원하지 않는 장소와 일시적 API 장애는 사용자가 취할 다음 행동도 다릅니다. 서버는 실패를 명시하고, Host는 재시도·다시 질문·기능 제한 중 어떤 정책을 적용할지 정해야 합니다.

연결 끊김 뒤 같은 호출을 다시 보낼 때에는 작업 성격도 봐야 합니다. 읽기 전용 시간표 조회와 외부 시스템에 예약을 만드는 도구의 재시도 위험은 다릅니다. MCP라는 전송 규약이 업무상 중복 실행을 자동으로 막아 주지는 않습니다.

## 13.4 에이전트에 날씨 도구 연결

![Host 안의 여행 정보 에이전트가 로컬 검색 도구를 직접 사용하고, 날씨 도구는 MCP Client를 통해 원격 MCP Server와 날씨 서비스에 연결하는 구조.](/images/ai-agents-and-applications/figure-13-06.png "그림 13.6. 로컬 검색과 원격 날씨 MCP 도구의 결합. 출처: AI Agents and Applications, 13장.")

같은 직원이 사내 장부는 직접 보고, 외부 업체에는 정해진 창구로 문의하는 모습입니다. 왼쪽 Host 경계 안의 검색 도구와 오른쪽 원격 날씨 서비스는 실행 위치와 장애 원인이 다릅니다. 아래 시간표 실습은 stdio 서버와의 연결·호출을 확인하는 범위이고, 이 그림의 원격 날씨 서비스까지 배포한 것은 아닙니다.

### 13.4.1 기존 여행 에이전트 준비

기존 모의 날씨 함수와 도구를 제거하고 실제 MCP 도구를 연결합니다. 같은 목적의 모의 도구와 실제 도구가 함께 등록되면 모델이 엉뚱한 쪽을 선택할 수 있습니다.

로컬 도구와 원격 도구의 이름과 설명이 비슷해도 결과의 신뢰도와 수명은 다릅니다. 현재 관측 데이터라는 의미가 도구 응답에 드러나야 합니다.

### 13.4.2 원격 도구 통합

서버에서 받은 도구를 프레임워크 도구 형태로 연결합니다. 이때 Client와 연결의 수명이 실제 도구 실행까지 유지되는지 확인해야 합니다.

도구 목록을 가져온 함수가 끝난 뒤 연결을 닫아 버리면 나중에 모델이 선택한 도구를 실행하지 못할 수 있습니다. 사용하는 어댑터가 세션과 연결을 어떻게 관리하는지 확인합니다.

### 13.4.3 비동기 대화 루프

원격 I/O를 기다리는 경로에 맞춰 비동기 호출을 사용합니다. `ainvoke`와 도구의 비동기 실행을 연결할 수 있습니다.

비동기는 기다리는 동안 다른 작업을 처리하는 데 도움을 줄 뿐, 원천 API를 빠르게 만들거나 실패를 없애지는 않습니다. 취소와 시간 제한, 동시 요청 수를 따로 관리해야 합니다.

### 13.4.4 로컬과 원격 도구 결합

로컬 여행 검색 도구와 원격 날씨 도구를 함께 등록할 수 있습니다. 모델은 제공된 정의를 보고 선택하지만 실행 계층은 서로 다릅니다.

로그에서 로컬 검색 실패와 MCP 연결 실패, 원천 날씨 API 실패를 구분해야 합니다. 모두 “도구 오류” 하나로 남기면 원인 조사가 어렵습니다.

### 13.4.5 통합 확인

먼저 도구 목록에 기대한 이름과 스키마가 있는지 보고 실제 에이전트 요청에서 서버가 호출됐는지 확인합니다.

정상 날씨 답변처럼 보여도 과거 대화나 모델 지식에서 나온 것일 수 있습니다. 원격 호출 기록과 관측 시점, 반환 장소를 연결해야 실제 도구 사용을 확인할 수 있습니다.

### 13.4.6 복합 질의

여행 문서에서 장소를 찾고 각 장소의 날씨를 조회한 뒤 조건을 비교합니다. 장소 이름을 전달하는 단계부터 같은 대상인지 확인해야 합니다.

날씨가 좋은 곳을 찾는 과정은 계절과 날짜, 사용자 기준에 영향을 받습니다. 모든 장소의 실시간 조회가 실패했는데 모의 데이터로 채워 성공처럼 답하는 것은 피해야 합니다.

## 실습: 서버 프로세스를 통한 도구 호출

외부 날씨 API를 붙이기 전에 실습용 시간표 도구로 프로토콜 왕복을 확인했습니다. 아래는 공식 Python SDK의 `mcp.server.fastmcp`를 사용하는 예제입니다. 별도 `fastmcp` 패키지와 혼용하지 않습니다.

첫 번째 파일은 `ch13_server.py`입니다.

```python
from mcp.server.fastmcp import FastMCP

server = FastMCP("study-timetable")

@server.tool()
def departure(town: str) -> dict:
    """Read a town's departure time from the fixed study timetable."""
    if town != "Perranporth":
        raise ValueError(f"No study timetable for {town}")
    return {
        "town": town, "departure": "09:00",
        "source": "study-timetable-v1",
    }

if __name__ == "__main__":
    server.run(transport="stdio")
```

두 번째 파일은 같은 폴더의 `ch13.py`입니다.

```python
import asyncio
import json
from pathlib import Path
import sys
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def main():
    parameters = StdioServerParameters(
        command=sys.executable,
        args=[str(Path(__file__).with_name("ch13_server.py"))],
    )
    async with stdio_client(parameters) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            discovered = await session.list_tools()
            print("Tools:", [tool.name for tool in discovered.tools])
            tool = next(t for t in discovered.tools if t.name == "departure")
            print("Required:", tool.inputSchema.get("required"))
            valid = await session.call_tool(
                "departure", arguments={"town": "Perranporth"},
            )
            if valid.isError:
                raise RuntimeError(str(valid.content))
            text = next(item.text for item in valid.content if item.type == "text")
            data = json.loads(text)
            print("Result:", data)
            assert data["departure"] == "09:00"
            missing = await session.call_tool(
                "departure", arguments={"town": "Unknown"},
            )
            print("Missing town is error:", missing.isError)
            assert missing.isError

if __name__ == "__main__":
    asyncio.run(main())
```

```powershell
python ch13.py
```

클라이언트가 서버를 자식 프로세스로 시작하므로 서버를 별도로 실행할 필요는 없습니다. `initialize()` 뒤 `list_tools()`에서 `departure`를 찾고, `town`이 필수 입력인지 확인한 뒤 호출합니다.

정상 호출에는 `09:00`과 출처가 반환됐고, 없는 장소에는 `isError=True`가 반환됐습니다. 같은 Python 함수를 import해서 부른 것이 아니라 **stdio 연결을 거친 별도 프로세스 호출**입니다.

### 서버와 클라이언트 코드를 연결해서 읽기

서버의 `@server.tool()`은 `departure`의 이름·설명·인자 스키마를 노출합니다. 클라이언트는 함수를 import하지 않고 `list_tools()`로 그 정의를 받습니다. 그래서 `Required`에 `town`이 나타나는 것을 확인할 수 있습니다. 도구 이름이 같아도 배포된 서버의 스키마가 바뀌었다면 발견 결과부터 다시 검사해야 합니다.

`StdioServerParameters`의 `sys.executable`은 클라이언트를 실행한 Python을 서버 실행에도 사용합니다. 환경이 달라 서버에서만 `mcp`를 import하지 못하는 문제를 줄이는 선택입니다. 서버 경로도 클라이언트 파일의 위치를 기준으로 만들어 현재 작업 폴더에 덜 의존하도록 했습니다.

두 `async with` 블록은 전송과 세션의 수명을 감쌉니다. 그 안에서 초기화, 발견, 두 번의 도구 호출이 이루어지고 블록을 벗어나며 자원을 정리합니다. `async`를 썼다는 이유로 두 호출을 동시에 실행하는 것은 아닙니다. 정상 결과를 검토한 다음 없는 장소를 순서대로 호출합니다.

SDK 반환값의 `isError`는 내용을 해석하기 전에 확인합니다. 정상 텍스트 콘텐츠를 JSON으로 읽은 뒤에야 `departure`를 검사합니다. 서버와 통신했다는 사실, 도구가 성공했다는 사실, 필요한 값이 맞다는 사실을 각각 확인하는 흐름입니다.

### Inspector에서 같은 도구 호출하기

클라이언트 코드 다음에는 Inspector에서 입력 스키마와 반환값을 확인했습니다. Inspector 2.12.0은 Node.js 22.19.0 이상이 필요합니다. 가상환경을 활성화한 상태에서 서버 파일과 같은 폴더에 `mcp-inspector.json`을 저장합니다.

```json

  "mcpServers": {
    "study-timetable": {
      "command": "python",
      "args": ["ch13_server.py"],
      "env": {
        "PYTHONUTF8": "1"
      }
    }
  }
}
```

```powershell

```

터미널에 표시된 로컬 접속 주소를 열고 `study-timetable`의 연결 스위치를 켭니다. `Tools`에서 `departure`를 선택하면 필수 입력 `Town`이 나타납니다. `Perranporth`를 넣고 `Execute Tool`을 실행했습니다.

![MCP Inspector에서 departure 도구를 호출해 Perranporth의 출발 시간 09:00과 출처 study-timetable-v1을 확인한 결과.](/images/ai-agents-and-applications/study-ch13-mcp-inspector.png "departure 도구의 반환값.")

결과의 `town`, `departure`, `source`가 Python 클라이언트의 반환값과 일치했습니다. 결과 패널을 닫으면 입력 폼으로 돌아갑니다. `Unknown`으로 바꿔 호출하면 없는 시간표를 정상 응답으로 채우지 않고 오류로 처리하는지도 비교할 수 있습니다.

이번 클라이언트는 도구 이름을 직접 지정했으므로 MCP 호출 성공이 모델의 도구 선택 능력을 보여 주지는 않습니다. 모델의 선택은 11장의 도구 루프에 연결해 별도로 평가해야 합니다.

흔한 함정: stdio 서버에서 디버깅용 `print()`를 stdout으로 보내면 프로토콜 메시지와 섞일 수 있습니다. 로그는 stderr를 사용합니다. 네트워크 HTTP 전송으로 바꾸면 인증·TLS·연결 수명도 추가로 다뤄야 합니다.

MCP에서 **연결·발견·호출·업무 결과**는 각각 다른 확인 단계입니다.

## 프로토콜 연결과 에이전트 통합의 차이

### 도구 발견과 모델의 도구 선택

발견이 된다는 것은 서버가 정의를 제공한다는 증거입니다. 그 정의가 모델에 바인딩됐는지, 설명이 질문에 맞는지, 실제 도구 요청을 실행하는 연결이 있는지는 따로 확인해야 합니다.

도구를 직접 호출해 정상 값을 받는 시험과 모델이 적절하게 선택하는 시험은 별개입니다. 두 시험을 섞으면 서버 오류인지 모델 선택 문제인지 좁히기 어렵습니다.

### MCP와 별도로 필요한 권한 통제

연결 규약과 권한 정책은 다릅니다. Host와 서버, 원천 서비스 각각에서 인증과 허용 범위를 확인해야 합니다.

### 직접 호출 시험과 에이전트 통합

모델이 올바른 도구와 인자를 선택하고 결과를 제대로 해석하는지는 별도 확인입니다.
