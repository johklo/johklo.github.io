도서관의 안내 데스크에 현재 호텔 빈방을 물으면 소개 책자는 찾을 수 있어도 재고는 알 수 없습니다. 질문에 맞는 창구를 고르는 것이 라우팅입니다. 소개 문서는 검색기로, 가격과 수량 조건은 DB로 보내야 합니다.

이번에는 모델에게 실행할 SQL 전체를 맡기는 대신 **검색 조건만 추출하게 하고, 허용된 조회는 코드가 작성**하도록 했습니다.

## 10.1 자료 저장소에 맞는 질의

벡터 저장소는 유사한 자료를 찾고 관계형 DB는 명시적인 조건과 관계로 행을 조회합니다. 그래프 DB는 개체 사이의 관계를 따라갑니다.

같은 “숙박 정보”라도 주변 분위기와 관광지 접근성은 문서에, 현재 가격과 재고는 거래 시스템에 있을 수 있습니다. 질문의 어떤 부분에 어떤 데이터가 필요한지 나눠야 합니다.

Dense retrieval은 임베딩 공간의 유사성을, sparse 또는 lexical retrieval은 단어의 출현과 가중치를 활용합니다. 메타데이터 필터는 그와 별도로 지역, 날짜, 문서 유형 같은 조건을 적용합니다.

## 10.2 Self-querying

Self-querying은 자연어 요청에서 의미 검색용 문장과 구조화된 필터를 함께 만드는 방식입니다. “Cornwall에 있는 박물관”에서 박물관을 검색할 표현과 지역 필터를 나눌 수 있습니다.

### 10.2.1 메타데이터 보강

검색할 기록에 지역, 출처, 자료 유형과 날짜 같은 필드를 준비합니다. 필터는 실제 저장한 값과 타입이 맞아야 동작합니다.

메타데이터를 모델로 생성한다면 틀린 태그도 들어갈 수 있습니다. 문서의 실제 지역과 모델이 추정한 지역을 구분하고, 허용 값과 누락 규칙을 정해야 합니다.

TF-IDF나 BM25는 주로 단어 기반 검색의 가중치와 순위를 위한 기법입니다. 지역 같은 명시적 메타데이터와 같은 것으로 취급하면 안 됩니다.

### 10.2.2 메타데이터가 있는 자료에 질의

직접 필터를 지정하거나 `SelfQueryRetriever`처럼 모델이 필터를 생성하는 구성 요소를 사용할 수 있습니다. 필드 설명과 허용 연산을 제공해야 잘못된 열 이름과 조건을 줄일 수 있습니다.

예를 들어 `region = "Cornwall"`과 의미 검색 문장 “가족이 방문할 박물관”을 함께 적용할 수 있습니다. 검색 대상이 줄어 정밀도가 좋아질 수 있지만 잘못 만든 필터는 필요한 자료를 완전히 제외합니다.

사용자 권한은 모델이 생성하는 필터에 맡기지 않습니다. 애플리케이션이 허용한 범위를 별도로 강제한 뒤 그 안에서 검색 조건을 적용해야 합니다.

## 10.3 구조화된 SQL 생성

자연어를 SQL로 바꾸려면 모델이 실제 테이블과 열, 관계를 알아야 합니다. 문법이 맞는 SQL도 존재하지 않는 열을 쓰거나 조인을 잘못하면 답이 틀립니다.

### 10.3.1 SQLite

SQLite는 하나의 파일을 DB로 사용하고 별도 서버 없이 접근할 수 있어 실습에 편합니다. 하지만 이 실행 방식이 외부 서비스와 같은 운영 조건을 제공한다는 뜻은 아닙니다.

SQL 문법과 사용 가능한 기능도 DB별로 다릅니다. SQLite 예제를 그대로 PostgreSQL에 적용할 수 있다고 가정하면 안 됩니다.

### 10.3.2 DB 구성과 연결

여행 예제는 목적지, 숙소와 특가 정보를 테이블로 나누고 키로 연결합니다. 모델에는 실제 스키마와 필요한 관계를 제공합니다.

숙소와 특가를 잘못 조인하면 같은 제안이 여러 번 나오거나 다른 지역의 가격이 붙을 수 있습니다. 테이블을 읽을 수 있는 것과 올바른 관계로 답하는 것은 다릅니다.

### 10.3.3 자연어에서 SQL 생성

질문, 스키마, DB 종류와 필요한 예시를 이용해 SQL을 만듭니다. 생성 결과에 코드 블록이나 설명이 붙을 수 있으므로 SQL 추출과 구문 검사도 필요합니다.

“이번 주말”처럼 상대적인 날짜를 사용하면 기준 날짜와 시간대가 명확해야 합니다. “가장 저렴한”이라는 표현도 총액인지 1박 요금인지, 객실 수와 세금이 포함되는지에 따라 질의가 달라집니다.

### 10.3.4 SQL 실행

생성과 실행은 분리된 책임입니다. 모델이 SQL을 만들 수 있다는 이유로 운영 DB에 임의 실행 권한을 줘서는 안 됩니다.

읽기 전용 자격 증명, 허용 테이블과 연산, 행 수와 실행 시간 제한을 적용합니다. 사용자별 접근 범위도 DB 또는 애플리케이션에서 강제해야 합니다.

문자열에서 코드 블록 표시만 제거하는 것은 검증이 아닙니다. 쓰기나 관리 명령을 막고 의도한 조회만 허용하는 통제가 필요합니다. 파라미터가 있는 값은 DB 드라이버의 바인딩을 사용하는 편이 안전합니다.

## 10.4 의미 기반 SQL

### 10.4.1 일반 SQL

일반 SQL의 조건과 조인은 정확한 필드와 규칙을 기준으로 합니다. 문자열의 일치나 패턴 검색, 수치 비교와 집계를 수행할 수 있습니다.

의미적 유사성과 다르지만 표현력이 단순한 정확 일치에만 한정되는 것은 아닙니다. 전문 검색이나 DB별 확장 기능을 조합할 수도 있습니다.

### 10.4.2 의미 검색과 결합

pgvector 같은 확장을 사용하면 관계형 데이터와 벡터를 함께 두고 유사도 검색을 수행할 수 있습니다. “조용하고 해변 가까운 숙소”는 설명의 의미로 찾고 지역과 가격은 정확한 필터로 제한하는 식입니다.

이름의 유사성만으로 같은 사람이나 같은 지역을 확정하면 안 됩니다. 벡터는 후보 검색에 도움이 될 수 있지만 식별과 권한 판정은 별도 기준이 필요합니다.

### 10.4.3 임베딩 생성

검색할 설명 필드 등을 임베딩해 행과 연결합니다. 모델, 차원과 입력 구성 방식을 고정하고 원문 변경 때 갱신해야 합니다.

값이 바뀐 행에 오래된 임베딩이 남으면 질의 결과의 순위와 현재 내용이 어긋납니다. 데이터 갱신과 재임베딩의 일관성이 필요합니다.

### 10.4.4 의미 검색 실행

질문 벡터와 저장 벡터의 거리를 계산해 순서를 정합니다. 사용하는 연산자가 유클리드 거리인지 코사인 거리인지 확인해야 합니다.

SQL에서 벡터 값을 문자열로 임의 연결하기보다 지원되는 드라이버와 파라미터 타입을 사용합니다. 의미 순위가 높아도 가격이나 날짜 조건을 충족한다는 뜻은 아니므로 필터와 함께 해석해야 합니다.

### 10.4.5 자동 생성

의미 검색까지 포함한 질의를 모델이 생성하도록 할 수 있습니다. 그 경우에도 모델이 벡터 숫자를 상상해서 만드는 것이 아니라 임베딩 함수가 계산한 값을 쿼리에 전달해야 합니다.

모델이 선택할 수 있는 필드와 연산을 제한하고 실행 전에 검증합니다. 일반 SQL과 벡터 SQL 모두 실행 계층의 통제를 유지해야 합니다.

### 10.4.6 얻을 수 있는 이점

관계형 필터와 조인, 유사도 검색을 같은 데이터 구조에 결합할 수 있습니다. 원문과 임베딩이 다른 시스템에 흩어질 때보다 일관성 관리가 단순해질 수 있습니다.

반면 인덱스 크기와 갱신 비용, 근사 검색의 성능을 확인해야 합니다. 기존 DB에 넣는다는 사실만으로 모든 규모에서 효율적인 것은 아닙니다.

## 10.5 그래프 DB 질의

그래프는 개체를 노드로, 관계를 엣지로 표현합니다. 특정 장소가 어느 지역에 속하고 어떤 교통수단으로 이어지는지처럼 관계를 따라가는 질문에 유용할 수 있습니다.

RDF의 주어, 술어, 목적어와 SPARQL, 속성 그래프의 노드와 관계 및 Cypher 등은 서로 다른 표현과 질의 체계입니다. 실제 저장소의 스키마와 문법을 제공해야 합니다.

모델이 관계를 추론했다고 그 관계가 DB에 있는 사실은 아닙니다. 생성한 질의의 결과와 모델의 추가 추론을 구분해야 합니다. 그래프를 사용한다고 근거의 정확성이나 설명가능성이 자동으로 보장되지는 않습니다.

## 10.6 체인 라우팅

질문을 보고 적절한 검색 경로를 선택합니다. 일반 관광 정보는 문서 검색, 실제 숙박 제안은 관계형 DB처럼 나눌 수 있습니다.

![Question router가 질문을 목적지 벡터 DB 또는 숙박 SQL DB 경로로 보내고, 선택한 검색 결과와 원래 질문으로 최종 응답을 생성하는 구조.](/images/ai-agents-and-applications/figure-10-06.png "그림 10.6. 여러 검색 경로를 가진 RAG. 출처: AI Agents and Applications, 10장.")

안내 데스크가 관광 안내는 자료실로, 객실 가격은 예약 장부로 보내는 모습입니다. 가운데 갈림길은 저장소 선택이고, 위쪽 점선은 **원래 질문을 답변 생성 단계에도 보존**하는 경로입니다. 두 저장소를 그렸다고 매번 둘 다 조회하는 것은 아닙니다. 또한 SQL을 만드는 상자가 실행 권한까지 부여하는 것은 아니므로 아래 실습에서는 모델의 필터 선택과 DB 실행을 분리했습니다.

### 10.6.1 검색 경로 준비

각 경로는 같은 입력을 받아 최종 생성에 사용할 근거를 반환하도록 구성할 수 있습니다. 다만 문서와 SQL 행의 의미가 다르므로 공통으로 보낼 때 구조를 명시해야 합니다.

필드 이름이 없는 튜플의 숫자를 모델이 알아서 해석하게 두면 가격과 할인율을 혼동할 수 있습니다. 열 이름과 단위를 포함한 구조가 더 명확합니다.

### 10.6.2 Router

모델이 허용된 경로 중 하나를 선택하도록 구조화된 출력을 사용합니다. 선택할 범주는 열거형 등으로 제한합니다.

복합 질문을 한 경로로 강제로 보내면 일부 요구를 놓칩니다. 두 저장소가 모두 필요한지, 추가 확인이 필요한지 판단하는 정책도 필요합니다. 모든 입력을 한 경로에 우겨 넣는 기본값은 실패를 감출 수 있습니다.

### 10.6.3 전체 RAG 연결

라우터의 선택에 따라 실제 검색을 수행하고 결과와 원래 질문으로 답을 만듭니다. 어떤 경로를 골랐는지와 검색한 근거를 함께 추적해야 합니다.

라우팅이 잘못되면 이후 검색과 생성이 정상 실행돼도 답은 틀릴 수 있습니다. 최종 문장 평가 외에 경로 선택 자체의 정답도 비교할 필요가 있습니다.

## 10.7 검색 결과 후처리

### 10.7.1 유사도 기준

관련도가 낮은 후보를 제외하거나 거리가 큰 후보를 제거합니다. 저장소별 점수의 의미와 범위를 확인해야 하며 같은 임계값을 모든 모델에 적용하면 안 됩니다.

필터 뒤 결과가 없으면 근거 부족으로 다룹니다. 무조건 한 개를 남기면 관계없는 자료가 최종 답의 근거가 될 수 있습니다.

### 10.7.2 키워드 기준

필수 단어와 제외 단어로 자료를 거를 수 있습니다. 명시적인 제약을 반영하기 쉽지만 동의어와 부정 표현, 언어 차이에 취약합니다.

“무료가 아니다”에도 “무료”라는 단어는 있습니다. 단어 존재만으로 문서의 의미를 판단할 수 없다는 한계를 기억해야 합니다.

### 10.7.3 시간 가중치

최근 접근한 자료나 최근 생성된 자료에 가중치를 줄 수 있습니다. 다만 최근 접근은 자료의 실제 최신성과 다릅니다.

오래된 문서를 자주 검색하면 접근 시간이 계속 갱신될 수 있습니다. 규정과 요금처럼 현재 유효한 자료가 중요한 경우에는 발행일, 적용일과 원천 버전을 기준으로 판단해야 합니다.

### 10.7.4 RRF

Reciprocal Rank Fusion은 여러 검색 결과의 순위를 결합합니다. 서로 척도가 다른 점수를 직접 더하지 않고 각 목록에서의 순위를 사용합니다.

개념적인 점수는 다음과 같습니다.

```text
RRF(d) = 각 검색 목록에서 d가 나온 경우의 1 / (c + rank(d)) 합
```

`c`는 순위 차이의 영향을 완화하는 상수입니다. 실제 구현에서는 순위가 0부터인지 1부터인지와 상수 설정을 일관되게 해야 합니다. 반환 문서 수 `k`와 혼동하지 않습니다.

두 목록에서 문서 A가 각각 1위와 4위, B가 2위와 2위라면 두 문서의 각 역순위 점수를 합쳐 비교합니다. 한 목록에만 등장한 문서는 그 목록의 기여만 가집니다.

합치려면 동일 문서를 식별할 ID가 필요합니다. 제목이 같다는 이유로 다른 버전의 문서를 하나로 보거나 같은 청크를 별개로 세면 순위가 왜곡됩니다. RRF도 근거가 틀렸는지 판단하는 사실 검증은 아닙니다.

## 직접 해보기: 모델의 판단과 DB 실행 권한 분리하기

`ch10.py`로 저장합니다. 작은 합성 숙소 DB를 메모리에 만들고, 자연어의 지역·가격 조건을 구조화합니다.

```python
import sqlite3
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import JsonOutputParser
from langchain_ollama import ChatOllama

class HotelFilter(BaseModel):
    model_config = ConfigDict(extra="forbid")
    town: Literal["Falmouth", "Truro"]
    max_price: int = Field(ge=1, le=500)

prompt = ChatPromptTemplate.from_template(
    'Extract hotel filters. Return only JSON with "town" and "max_price". '
    'town must be Falmouth or Truro; max_price is pounds per night. '
    'Request: {question}'
)
filters = HotelFilter.model_validate((
    prompt | ChatOllama(
        model="llama3.2:latest", temperature=0, format="json", num_predict=100,
    ) | JsonOutputParser()
).invoke({"question": "Find study hotels in Falmouth for at most 100 pounds per night."}))
with sqlite3.connect(":memory:") as connection:
    connection.execute("CREATE TABLE hotels(name TEXT, town TEXT, price INTEGER)")
    connection.executemany("INSERT INTO hotels VALUES (?, ?, ?)", [
        ("Harbour", "Falmouth", 80),
        ("Cliff", "Falmouth", 140),
        ("Station", "Truro", 60),
    ])
    connection.execute("PRAGMA query_only = ON")
    rows = connection.execute(
        "SELECT name, town, price FROM hotels "
        "WHERE town = ? AND price <= ? ORDER BY price LIMIT 5",
        (filters.town, filters.max_price),
    ).fetchall()
print("Validated filter:", filters.model_dump())
print("Rows:", rows)
assert rows == [("Harbour", "Falmouth", 80)]
```

```powershell
python ch10.py
```

출력된 필터는 `town=Falmouth`, `max_price=100`이었고, 결과에는 `Harbour / Falmouth / 80` 한 행만 남았습니다. 다른 지역의 더 저렴한 숙소와 같은 지역의 예산 초과 숙소가 제외됐는지 확인했습니다.

모델은 지역과 최대 가격만 정했습니다. 테이블 이름·조회 열·정렬·행 수는 코드가 고정하고 값은 바인딩했습니다. 이 방법은 자유 SQL 생성보다 표현 범위가 좁지만, **사용자가 허용된 질문만 하는 서비스에서는 더 작은 권한으로 구현**할 수 있습니다.

`query_only`는 이 연결의 쓰기를 제한하는 실습 장치입니다. 운영에서는 DB 계정 자체의 읽기 권한과 사용자별 행 접근 범위, 시간 제한도 별도로 강제해야 합니다.

직접 확인할 질문: “조회 결과가 0개면 모델에게 다른 지역으로 바꿔 보라고 해도 될까요?” 사용자 조건을 바꾸는 것이므로 먼저 구분해 알려야 합니다. 빈 결과는 검색 실패나 시스템 장애와도 다릅니다.

실패 실험: 모델 출력 대신 `{"town": "Unknown", "max_price": -1}`을 검증하면 DB 실행 전에 중단됩니다. 오류를 임의의 기본 필터로 바꿔 정상 결과처럼 보여 주지 않습니다.

한 줄 정리: **모델이 고를 수 있는 조건과 DB가 허용할 작업은 서로 다른 경계**입니다.

## 질문

### 유효한 SQL이면 바로 실행해도 될까?

문법과 업무상 허용 범위는 다릅니다. 읽기 전용 권한과 실행 제한, 스키마와 조건 검증이 필요합니다.

### 가장 최근에 검색된 자료가 가장 최신 자료일까?

접근 시점과 내용의 유효 시점은 다릅니다. 시간 가중치가 무엇을 측정하는지 확인해야 합니다.
