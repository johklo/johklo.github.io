상담원이 “시간표를 확인하겠습니다”라고 말하는 것과 실제 조회 화면을 여는 것은 다릅니다. 에이전트도 모델이 낸 도구 요청을 프로그램이 실행하고, 그 결과를 다시 모델에게 줘야 합니다. 이 왕복이 빠지면 도구를 쓴 것처럼 말하는 답변만 남을 수 있습니다.

이번에는 **도구 요청·실행 결과·최종 답변의 세 메시지**가 실제로 연결되는지 확인했습니다.

## 11.1 도구 하나를 가진 여행 정보 에이전트

먼저 여행 문서를 검색하는 도구 하나를 제공합니다. 모델이 질문을 보고 검색을 요청하면 프로그램이 검색하고 그 결과를 돌려줍니다.

### 11.1.1 프로젝트 구성

도구 구현, 모델 설정, 상태와 그래프 구성을 구분합니다. 개별 도구를 직접 호출해 확인할 수 있어야 모델의 선택 오류와 도구 자체의 오류를 나눌 수 있습니다.

예제는 실행 원리를 보여 주기 위한 작은 프로그램입니다. 외부 호출의 시간 제한이나 인증, 입력 검증을 실제 서비스에서 생략해도 된다는 뜻은 아닙니다.

### 11.1.2 환경 변수

모델 API와 추적 서비스에 필요한 키를 실행 환경에서 읽습니다. 없는 키와 잘못된 키를 구분해 오류를 드러내야 합니다.

환경 변수의 이름과 실행 위치도 중요합니다. IDE에서 실행할 때와 터미널에서 실행할 때 읽는 설정 파일과 작업 디렉터리가 다르면 다른 환경으로 동작할 수 있습니다.

### 11.1.3 여행 정보 저장소

여행 문서를 읽고 나눠 벡터 저장소를 만듭니다. 매 질문마다 전체 원문을 다시 내려받고 임베딩하면 불필요한 시간과 비용이 발생합니다.

책은 공통 저장소 인스턴스를 재사용합니다. 재사용과 영속화는 다른 성질입니다. 한 프로세스에서 한 번 만들었다고 프로세스 재시작이나 원문 갱신까지 해결되지는 않습니다.

## 11.2 도구 호출

### 11.2.1 Function calling에서 tool calling으로

모델의 응답이 자연어 문장뿐 아니라 도구 호출 요청을 포함할 수 있습니다. 함수명과 구조화된 인자를 반환하고 프로그램이 실행하는 방식입니다.

도구의 종류와 제공자에 따라 실행 주체는 달라질 수 있습니다. 사용자 정의 함수는 보통 애플리케이션이 실행하고, 일부 제공자 내장 도구는 제공자 쪽에서 실행될 수 있습니다. 응답 프로토콜과 실행 경계를 구분해야 합니다.

### 11.2.2 도구 정의

`@tool` 같은 구성을 사용하면 함수 이름, 설명과 인자 스키마를 모델에 제공할 수 있습니다. 모델은 함수 본문을 읽고 실행하는 것이 아니라 이 정의를 보고 선택합니다.

설명에는 언제 사용하는지, 필요한 입력과 반환값이 무엇인지 들어가야 합니다. “검색 도구”처럼 막연한 설명보다 “현재 저장된 여행 문서에서 장소와 교통 정보를 찾는 도구”가 범위를 드러냅니다.

함수의 타입 힌트도 입력의 의미까지 전부 보장하지는 않습니다. 문자열이라는 조건을 만족해도 존재하지 않는 장소나 허용 범위 밖의 경로일 수 있습니다. 실행 전에 업무 조건과 권한을 확인해야 합니다.

### 11.2.3 모델에 바인딩

`bind_tools`는 모델 호출에 도구 정의를 연결합니다. 이 시점에 도구 함수가 실제 실행되는 것은 아닙니다.

모델이 도구 호출을 지원하는지, 사용하는 API와 라이브러리가 그 응답을 어떻게 표현하는지 확인해야 합니다. 도구를 등록했어도 모델은 호출 없이 자기 지식으로 답하려 할 수 있습니다.

### 11.2.4 에이전트 상태

기본 상태는 메시지 목록입니다. 사용자 질문, 모델의 도구 호출 요청, 도구 결과와 최종 답이 순서대로 들어갑니다.

새 노드의 메시지를 목록에 합칠 reducer가 필요합니다. 목록을 통째로 덮어쓰면 직전 도구 요청이나 사용자 질문을 잃을 수 있습니다.

동시에 여러 도구 요청이 생기면 각각을 구분할 호출 ID가 중요합니다. 어떤 결과가 어떤 요청에 대응하는지 연결해야 모델이 다음 판단을 할 수 있습니다.

### 메시지 네 개로 도구 왕복 읽기

전화로 재고를 문의하면 상담원의 요청, 창고의 답, 고객에게 하는 설명은 서로 다릅니다. 에이전트에서도 이 구분을 메시지로 남깁니다. 아래 호출 ID는 구조를 설명하기 위한 예시입니다.

```text
1. HumanMessage
   "Perranporth행 버스는 언제 출발하나요?"

2. AIMessage
   tool_calls:
     id = call-example-1
     name = lookup_departure
     args = {"town": "Perranporth"}

3. ToolMessage
   tool_call_id = call-example-1
   content = {"departure": "09:00", "source": "study-timetable-v1", ...}

4. AIMessage
   "시간표의 출발 시각은 09:00입니다."
```

2번은 조회가 끝난 결과가 아니라 **조회해 달라는 요청**입니다. 3번을 만드는 것은 애플리케이션이고, 4번은 그 관측 결과를 읽은 모델의 설명입니다. 도구 사용의 증거를 찾을 때는 4번 문장에 “조회했다”는 표현이 있는지보다 2번과 3번의 연결을 봐야 합니다.

도구 호출이 두 개라면 각각의 요청 ID와 결과 ID를 맞춰야 합니다. 결과를 자연어 human 메시지로 다시 넣으면 도구 응답이라는 역할과 호출 연결을 잃습니다. 구조화된 메시지를 유지하는 이유가 여기에 있습니다.

### 11.2.5 도구 실행

실행 노드는 모델의 마지막 메시지에서 호출 요청을 꺼냅니다. 허용된 이름인지와 인자를 검증하고 해당 함수를 실행한 뒤, 결과를 `ToolMessage`로 만들어 요청 ID와 연결합니다.

도구 결과가 “자료 없음”인지 “외부 서비스 실패”인지 구분해야 합니다. 둘을 같은 빈 문자열로 바꾸면 모델이 실패한 조회를 정상적인 부재로 해석할 수 있습니다.

부작용이 있는 도구는 재시도를 더 신중히 다뤄야 합니다. 조회는 다시 해도 되지만 예약이나 결제 요청은 중복 실행될 수 있습니다. 도구 호출 ID와 업무상의 중복 방지 키가 같은 의미인지도 확인해야 합니다.

### 11.2.6 모델 노드

모델 노드는 현재 메시지와 지침을 보내 새 응답을 받습니다. 결과에 도구 호출 요청이 있으면 실행 노드로, 더 이상 없으면 종료로 보냅니다.

도구 호출과 자연어 내용이 함께 반환될 수도 있으므로 응답 전체를 단순 문자열이라고 가정하지 않습니다. 스트리밍이라면 호출 인자가 여러 조각으로 도착할 수도 있습니다.

## 11.3 그래프 조립

시작점은 모델 노드입니다. 조건부 경로가 도구 요청 유무를 확인하고, 도구 실행 뒤에는 다시 모델로 돌아갑니다.

![시작 노드에서 모델 노드로 들어간 뒤 도구 호출이 있으면 tools로, 없으면 종료로 이동하고 도구 결과는 다시 모델 노드로 돌아오는 에이전트 그래프.](/images/ai-agents-and-applications/figure-11-02.png "그림 11.2. 모델과 도구 실행을 연결한 그래프. 출처: AI Agents and Applications, 11장.")

그림은 작은 구조지만 실제 모델 호출은 여러 번 생길 수 있습니다. 도구 호출을 결정하는 첫 응답과 도구 결과를 읽고 최종 답을 만드는 다음 응답은 다른 호출입니다.

## 11.4 실행 구조

ReAct는 판단과 행동, 관측 결과를 반복해서 사용하는 패턴입니다. 이 구현에서는 메시지에 나타난 도구 요청과 실행 결과를 통해 반복을 확인할 수 있습니다.

모델이 내놓는 설명을 내부 사고의 완전한 기록처럼 취급할 필요는 없습니다. 실제로 검증할 수 있는 것은 어떤 도구를 어떤 인자로 요청했고 프로그램이 무엇을 실행해 어떤 결과를 받았는지입니다.

종료 조건도 필요합니다. 모델이 계속 같은 도구를 호출하면 반복 횟수와 시간, 비용 예산으로 중단할 수 있어야 합니다. 중단한 상태를 최종 답변 완료와 구분합니다.

## 11.5 REPL

REPL은 입력을 읽고 실행하고 결과를 보여 주는 반복 인터페이스입니다. 콘솔에서 사용자의 질문을 받아 메시지로 만들고 그래프 결과를 출력합니다.

반복 인터페이스가 있다고 이전 대화가 저장되는 것은 아닙니다. 매번 새 상태로 호출하면 각 질문은 독립적입니다. 대화 이력과 체크포인트는 따로 연결해야 합니다.

## 11.6 요청 하나 따라가기

### 11.6.1 단계별 디버깅

한 요청에서 최소한 다음 항목을 확인할 수 있어야 합니다.

| 위치 | 확인할 내용 |
| --- | --- |
| 입력 | 실제 사용자 질문과 system 지침 |
| 모델 응답 | 호출한 도구 이름과 인자, 호출 ID |
| 실행 노드 | 어떤 함수가 실제 실행됐는지 |
| 도구 결과 | 원문, 값과 오류 상태 |
| 다음 모델 호출 | 도구 결과가 올바른 역할과 ID로 들어갔는지 |
| 종료 | 최종 답인지 예산 초과나 실패인지 |

도구를 실행하지 않았는데 답이 나왔다면 모델이 추측했을 수 있습니다. 반대로 도구를 실행했어도 결과를 잘못 사용하면 답이 틀릴 수 있습니다. 도구 사용률 자체가 정답률은 아닙니다.

## 11.7 날씨 도구 추가

### 11.7.1 모의 날씨 서비스

책은 처음에 임의의 날씨와 온도를 반환하는 모형을 사용합니다. 목적은 현재 날씨의 정확성을 확인하는 것이 아니라 도구 선택과 여러 호출의 흐름을 관찰하는 것입니다.

모의 데이터를 실제 관측값처럼 해석하면 안 됩니다. 테스트를 반복 가능하게 하려면 무작위 결과보다 고정된 응답을 사용하는 경우도 유용합니다.

### 도구 설명은 선택 기준이고 함수 본문은 실행입니다

모델에 보이는 것은 도구 이름·설명·인자 스키마입니다. 함수 안에서 SQL을 실행하는지, 원격 API를 부르는지, 고정된 값을 반환하는지는 그 설명만으로 모두 알 수 없습니다.

| 정의할 항목 | 시간표 도구의 예 | 누락됐을 때 생길 문제 |
| --- | --- | --- |
| 사용하는 상황 | 실습 시간표의 출발 시각 조회 | 모델이 일반 지식으로 대신 답함 |
| 지원 범위 | Perranporth 한 장소 | 다른 장소를 넣어도 될 것으로 오해 |
| 입력 의미 | 정확한 장소명 | 별칭·출발지·도착지를 혼동 |
| 결과 의미 | 시각과 출처 ID | 현재 실시간 정보로 과대 해석 |
| 실패 의미 | 지원하지 않는 장소는 오류 | 없는 시간표를 정상 값처럼 사용 |

설명을 개선하면 선택 오류를 줄일 수 있지만, 실행 코드의 검증을 없애지는 않습니다. 모델이 허용되지 않은 장소를 요청하면 함수 실행 경계에서도 막아야 합니다. 반대로 도구의 검증이 엄격해도 모델이 올바른 도구를 고르지 않으면 사용자 요청은 해결되지 않습니다. 선택과 실행은 별도 평가 대상입니다.

### 11.7.2 날씨 도구

도구는 장소를 받아 해당 장소의 조건과 온도를 반환합니다. 장소를 찾을 수 없는 경우와 서비스가 실패한 경우를 구분합니다.

실제 서비스로 바꾸면 날짜와 시간대, 온도 단위, 현재 관측과 예보의 차이도 필요합니다. “날씨가 좋다”는 판단에는 어떤 시간과 기준을 사용했는지 드러나야 합니다.

### 11.7.3 여러 도구 등록

여행 검색과 날씨 도구를 모델에 함께 등록합니다. 그래프의 기본 루프는 유지하면서 모델이 도구를 선택할 수 있습니다.

그러나 도구 수가 늘면 역할이 겹치거나 입력을 잘못 전달하는 경우도 늘어납니다. 도구 설명과 출력 규격을 명확히 하고 조합 요청을 따로 시험해야 합니다.

## 11.8 여러 도구 실행

### 11.8.1 초기 동작

모델은 “좋은 날씨의 해안 마을”을 묻는 질문에 관광지를 자기 지식으로 정하고 날씨만 조회할 수 있습니다. 그러면 저장된 여행 자료를 사용한다는 의도가 지켜지지 않을 수 있습니다.

도구를 제공하는 것과 반드시 근거로 사용하게 만드는 것은 다릅니다. 실제 트레이스에서 어떤 단계를 생략했는지 확인해야 합니다.

### 11.8.2 System 지침 보완

장소는 여행 검색 도구에서 찾고, 날씨는 날씨 도구로 확인하도록 지침과 설명을 구체화합니다. 호출 순서를 반드시 지켜야 하는 요구라면 그래프에서도 그 순서를 강제할 수 있습니다.

자연어 지침은 동작을 유도하지만 권한이나 강제 정책의 대체물이 아닙니다. 외부 행동의 허용 범위는 실행 코드에서 검사해야 합니다.

### 두 도구를 호출하는 순서는 언제 정해질까요?

“A와 B의 날씨를 비교”한다면 장소가 이미 정해져 있으므로 두 날씨 조회는 독립적일 수 있습니다. 반면 “교통이 편한 해안 마을을 찾고 그곳의 날씨를 확인”한다면 먼저 마을을 찾아야 합니다. 앞 도구의 결과가 뒤 도구의 입력을 결정하는 데이터 의존성입니다.

```text
순차 의존:
  여행 검색 → 선정된 장소 → 해당 장소의 날씨 → 종합 답변

독립 호출:
  A의 날씨 ─┐
  B의 날씨 ─┴→ 비교 답변
```

모델이 한 응답에서 여러 `tool_calls`를 만들 수 있다는 사실과, 그 호출들을 모두 병렬 실행해도 된다는 사실은 다릅니다. 필수 순서가 있는 업무라면 그래프나 실행 정책으로 보장해야 합니다. “반드시 검색부터 하라”는 문장만으로 거래나 권한 규칙을 맡기지 않습니다.

중단 정책도 전체 루프를 기준으로 정합니다. 모델 호출 예산, 도구별 시간 제한, 전체 요청 마감은 서로 다른 제한입니다. 하나의 느린 도구가 모델 호출을 거의 쓰지 않은 채 전체 시간을 소모할 수도 있으므로 호출 횟수만 제한해서는 충분하지 않습니다.

## 11.9 사전 구성 에이전트

### 11.9.1 기본 루프 재사용

책은 수동으로 만든 도구 실행 루프를 사전 구성 ReAct 에이전트로 바꿉니다. 반복 코드가 줄어들지만 어떤 상태 스키마와 종료 규칙을 사용하는지 이해해야 합니다.

사전 구성 에이전트의 생성 함수와 import 경로는 버전에 따라 달라질 수 있습니다. 책의 API와 현재 LangChain, LangGraph 문서의 권장 API를 섞지 않습니다.

### 11.9.2 실행 결과

자연어 문자열뿐 아니라 텍스트 블록 등 구조화된 응답이 나올 수 있습니다. 화면에 출력할 본문과 추적할 메타데이터를 분리합니다.

추상화를 바꾼 뒤에는 이전과 같은 입력으로 도구 선택과 최종 결과가 유지되는지 비교해야 합니다. 코드가 짧아졌다는 사실은 기능 동등성의 증거가 아닙니다.

### 11.9.3 LangSmith 관측

프레임워크 내부 루프를 직접 디버깅하기 어려울 때 트레이스로 모델과 도구 호출을 연결합니다. 결과가 어느 도구의 값에 의존했는지와 어디서 시간이 걸렸는지 볼 수 있습니다.

### 11.9.4 추적 설정

추적 프로젝트와 인증 정보를 설정한 뒤 실제 요청이 기록되는지 확인합니다. 기록이 활성화되면 사용자 질문과 도구 결과도 외부 추적 시스템에 전송될 수 있습니다.

민감한 입력을 무조건 모두 남기지 않고 수집 범위와 접근 권한, 보존 정책을 정합니다. 관측을 위해 정보를 모으는 일에도 데이터 경계가 필요합니다.

## 직접 해보기: 모델이 요청한 도구를 LangGraph로 실행하기

`ch11.py`로 저장합니다. 시간표 값은 실습용 고정 데이터입니다. 모델은 로컬 `llama3.2`를 사용하고, 도구 실행은 실제 `ToolNode`가 담당합니다.

```python
from typing import Annotated, Literal, TypedDict
from langchain_core.messages import HumanMessage, SystemMessage, ToolMessage
from langchain_core.tools import tool
from langchain_ollama import ChatOllama
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode

@tool
def lookup_departure(town: Literal["Perranporth"]) -> dict:
    """Look up the departure time in the study timetable for Perranporth."""
    return {"town": town, "departure": "09:00", "source": "study-timetable-v1"}

class State(TypedDict):
    messages: Annotated[list, add_messages]
    calls: int

model = ChatOllama(
    model="llama3.2:latest", temperature=0, num_predict=180,
).bind_tools([lookup_departure])

def assistant(state):
    if state["calls"] >= 3:
        raise RuntimeError("Model-call budget exhausted")
    reply = model.invoke([
        SystemMessage(content="Use lookup_departure for timetable facts. "
                      "After receiving the result, answer with its time and source."),
        *state["messages"],
    ])
    return {"messages": [reply], "calls": state["calls"] + 1}

builder = StateGraph(State)
builder.add_node("assistant", assistant)
builder.add_node("tools", ToolNode([lookup_departure], handle_tool_errors=False))
builder.add_edge(START, "assistant")
builder.add_conditional_edges(
    "assistant",
    lambda state: "tools" if state["messages"][-1].tool_calls else "done",
    {"tools": "tools", "done": END},
)
builder.add_edge("tools", "assistant")
result = builder.compile().invoke({
    "messages": [HumanMessage(content="Use the study timetable tool: "
                              "when does the bus to Perranporth leave?")],
    "calls": 0,
}, config={"recursion_limit": 10})
for message in result["messages"]:
    print(message.type, getattr(message, "tool_calls", []), message.content)
tools = [m for m in result["messages"] if isinstance(m, ToolMessage)]
assert tools, "The model did not use the timetable tool"
assert "09:00" in tools[0].content
assert "09:00" in result["messages"][-1].content
```

```powershell
python ch11.py
```

모델이 요청을 낸 첫 `AIMessage`와, 실행 결과를 담은 `ToolMessage`, 최종 `AIMessage`를 구분해서 읽습니다. `ToolMessage.tool_call_id`는 어느 호출 요청에 대한 결과인지 연결합니다. 예쁜 최종 문장보다 **실행 결과가 실제로 메시지에 들어왔는지**를 먼저 확인했습니다.

### `add_messages`와 `ToolNode`가 각각 하는 일

`assistant()`는 새로운 모델 메시지 한 개를 반환합니다. `messages` 필드에 지정한 `add_messages`는 이를 기존 메시지 상태에 반영합니다. 일반적으로 새 메시지를 추가하고, 같은 메시지 ID가 있으면 갱신하는 방식이므로 단순한 문자열 덧붙이기와 다릅니다. 사용자 질문과 도구 요청·결과가 다음 모델 호출까지 남는 기반입니다.

`ToolNode`는 마지막 모델 응답의 도구 요청을 실행하고 대응하는 도구 메시지를 만듭니다. 모델에게 정의를 보여 주는 `bind_tools()`와 실제 도구 실행을 담당하는 `ToolNode`를 같은 단계로 보면 안 됩니다. 둘 사이에 있는 조건부 엣지가 `tool_calls`의 유무를 보고 경로를 고릅니다.

도구 오류는 `handle_tool_errors=False`로 숨기지 않도록 했습니다. 이 실습에서는 예외가 실행 실패로 드러납니다. 서비스에서 오류를 모델에 다시 알려 복구하게 하려면 어떤 오류가 재시도 가능한지, 몇 번까지 허용할지, 사용자에게 어떤 상태로 반환할지를 별도로 설계해야 합니다.

이번 실행은 `lookup_departure({"town": "Perranporth"})` 요청 후 도구 결과를 받아 `09:00`으로 답했습니다. 다만 최종 문장은 정확한 출처 ID 대신 “study timetable”이라고 표현했습니다. **도구 결과에 출처가 있다는 것과 최종 답이 출처 규격을 지킨다는 것도 다릅니다.** 정확한 ID가 필수라면 응답을 구조화하거나 프로그램이 검증된 출처를 별도 필드로 반환해야 합니다.

세 번의 모델 호출 예산은 성공을 보장하지 않습니다. 모델이 같은 도구를 계속 부르면 명시적으로 실패합니다. 호출 제한을 만나도 이전 문장을 완성된 답처럼 반환하지 않습니다.

직접 확인할 질문: “도구가 성공하면 답도 정확할까요?” 마지막 모델이 `09:00`을 다르게 옮길 수 있으므로 실행 값과 최종 답을 함께 검사해야 합니다.

실패 실험: `lookup_departure.invoke({"town": "Unknown"})`을 별도로 실행하면 허용 인자 검증에서 실패합니다. 도구를 모델에 노출하는 것과 실행 범위를 허용하는 것은 별개의 결정입니다.

한 줄 정리: 에이전트의 도구 사용은 **요청 ID·실행 결과·최종 해석을 연결해서** 확인합니다.

## 질문

### 북클럽 적용: 답은 맞았지만 도구 메시지가 없다면 성공일까요?

정답 문자열이 우연히 맞았을 수는 있습니다. 하지만 시간표 도구를 사용해야 하는 요구는 충족하지 못했습니다. 모델의 요청 메시지와 실제 도구 결과, 마지막 답변을 따로 확인해야 합니다.

반대로 도구 결과에 09:00이 있어도 마지막 답이 08:00이면 도구 사용은 성공하고 최종 해석은 실패한 것입니다. 결과와 경로를 각각 어떻게 채점할지 정해 봅니다.

### 도구를 바인딩하면 함수가 바로 실행되는가?

정의만 모델 호출에 전달됩니다. 실제 호출 요청을 받아 검증하고 실행하는 과정은 별도로 필요합니다.

### 도구를 항상 호출하게 만들면 답의 정확성이 보장되는가?

검색 결과가 틀리거나 인자와 해석이 잘못될 수 있습니다. 선택, 실행 결과, 최종 답을 각각 확인해야 합니다.
