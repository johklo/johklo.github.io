장표 하나하나가 맞아도 순서가 틀리면 듣는 사람은 결론에 도착하지 못한다. 컨설팅 회사와 발표 전문가들이 쓰는 스토리 구조는 몇 가지로 정리되는데, 모두 "듣는 사람이 다음 장에서 무엇을 궁금해할까"에 답하는 순서를 만든다. 원칙마다 예시를 붙이고, 30장이 넘는 기술 덱을 실제로 재배치한 과정을 함께 남긴다.

## 피라미드 원칙: 결론을 먼저 말한다

Barbara Minto가 McKinsey에서 정리한 방식이다. 맨 위에 결론 하나를 두고, 그 아래에 결론을 받치는 근거 3~4개를, 근거 아래에 데이터를 둔다. 읽는 사람은 첫 문장에서 답을 얻고, 더 알고 싶은 만큼만 아래로 내려간다.

근거를 묶을 때는 MECE(Mutually Exclusive, Collectively Exhaustive)를 지킨다. 근거끼리 겹치지 않고, 합치면 빠진 것이 없어야 한다. 겹치면 같은 말을 두 번 듣게 되고, 빠지면 "그럼 그건?"이라는 질문이 남는다.

예를 들어 운영 조직 임원에게 노드 유지보수 방식을 보고한다면 이렇게 쌓는다.

| 층 | 내용 |
| --- | --- |
| 결론 | 작업 전 기존 노드를 모두 cordon하고 1대씩 drain하면 Pod는 새 노드로 한 번만 옮겨진다 |
| 근거 1 | 스케줄러는 cordon된 노드를 점수 계산 전에 제외한다 |
| 근거 2 | cordon하지 않으면 새 노드가 차는 순간부터 Pod가 기존 노드로 간다 |
| 근거 3 | 영역 분산 규칙이 있는 앱은 cordon만으로 부족해 설정 확인이 필요하다 |
| 데이터 | 점수 계산 예시, 테스트 결과, 문서 링크 |

의사결정자가 듣는 자리라면 이 순서가 가장 빠르다. 결론에 동의하면 근거를 건너뛰고, 의심이 가면 해당 근거만 깊게 본다.

## SCQA: 상황, 문제, 질문, 답

Minto가 피라미드의 도입부를 쓰는 방법으로 제시한 구조다. 듣는 사람이 이미 아는 상황(Situation)에서 시작해, 그 상황을 흔드는 문제(Complication)를 보이고, 문제가 만드는 질문(Question)에 답(Answer)한다.

| 단계 | 역할 | 예시 |
| --- | --- | --- |
| Situation | 이견 없는 현재 상태 | 결제 서비스는 AKS 3개 영역에서 운영된다 |
| Complication | 상태를 바꾸는 사건 | 호스트 유지보수로 한 영역의 노드를 모두 비워야 하는데, drain한 Pod가 다음 작업 대상 노드로 가거나 Pending이 된다 |
| Question | 문제가 만드는 질문 | Pod를 원하는 노드로 한 번만 옮기려면 어떻게 해야 하나 |
| Answer | 답 | 갈 노드를 먼저 만들고, 가면 안 되는 노드를 먼저 막은 뒤 1대씩 비운다 |

질문이 뻔하면 Q를 생략한 SCR(Situation, Complication, Resolution)로 쓴다. 상황 설명이 길어지면 듣는 사람이 지루해하고, 문제가 약하면 답을 들을 이유가 생기지 않는다. 그래서 상황은 한두 문장으로 줄이고 문제에 힘을 싣는다.

피라미드와 SCQA는 답을 어디에 두느냐가 다르다. 경영진 보고는 SCQA를 한 장 요약으로 압축해 맨 앞에 두고 나머지를 근거로 붙인다. 교육이나 기술 세미나는 SCQA 순서를 덱 전체에 펼친다. 원리를 모르는 사람에게 답부터 주면 왜 그 답인지 받아들이지 못하기 때문이다.

## 수평 논리와 수직 논리: 제목만 읽어도 이야기가 이어진다

컨설팅 장표에서 자주 쓰는 점검 방법이다. 수평 논리는 장 제목을 순서대로 읽었을 때 이야기가 이어지는지, 수직 논리는 한 장 안의 도식과 수치가 그 장의 제목을 증명하는지를 본다.

이를 위해 제목을 주제가 아닌 결론 문장으로 쓰는 경우가 많다(action title).

| 주제형 제목 | 결론형 제목 |
| --- | --- |
| 스케줄러 점수 계산 | 빈 새 노드가 빈 자원 점수에서 24점 앞서 먼저 선택된다 |
| cordon 범위 비교 | 작업 대상만 cordon하면 6번째 Pod부터 기존 노드로 간다 |
| 타임아웃 설정 | 외부 결제 호출은 길게, 내부 DB 호출은 짧게 둔다 |

본문을 만들기 전에 제목만 적은 빈 덱(ghost deck)을 먼저 만들어 순서를 검토하면 재작업이 줄어든다. 한국 SI 장표처럼 제목을 명사구로 쓰는 관례가 있다면 제목 바로 아래 리드 문장에 결론을 쓰고, 리드만 이어 읽어 같은 점검을 한다.

한 장에는 메시지 하나만 둔다. 두 가지를 말하는 장은 둘로 나누고, 같은 결론을 두 장에 나눠 담았다면 하나로 합친다.

## Sparkline: 지금과 바뀐 모습을 오간다

Nancy Duarte가 Steve Jobs의 발표와 Martin Luther King Jr.의 연설 같은 명연설을 분석해 정리한 구조다. 좋은 발표는 "지금의 현실(what is)"과 "바뀔 수 있는 모습(what could be)"을 번갈아 보여 주며 둘 사이의 차이로 긴장을 만든다. 왕복할수록 지금 상태로 머무는 비용이 커 보이고, 마지막에 바뀐 세계(New Bliss)를 보여 주며 행동을 요청한다.

기술 발표에서는 이렇게 쓸 수 있다.

1. 지금: 노드를 비울 때마다 일부 요청이 실패한다.
2. 바뀐 모습: 작업 중에도 오류가 0건인 절차가 있다.
3. 지금: 그런데 Pod가 어디로 갈지 보장되지 않아 같은 Pod가 두세 번 옮겨진다.
4. 바뀐 모습: cordon 범위를 정하면 한 번만 옮겨진다.
5. 행동: 다음 유지보수 전에 이 절차로 리허설한다.

변화를 설득해야 하는 자리, 예를 들어 새 운영 방식을 도입하자고 제안할 때 효과가 크다.

## ABT: And, But, Therefore

과학자 출신 영화감독 Randy Olson이 제안한 한 문장 구조다. "A이고 B다(And). 그런데 C다(But). 그래서 D한다(Therefore)." SCR을 한 문장으로 줄인 셈이라 요약, 메일 첫 문단, 장표 리드에 쓰기 좋다.

> 결제 서비스는 3개 영역에 분산되어 있고 노드 작업 절차도 있다. 그런데 절차대로 drain해도 Pod가 다음 작업 대상 노드로 가서 다시 옮겨진다. 그래서 작업 전에 대상 영역의 노드를 모두 cordon하는 단계를 추가한다.

"그리고"만 이어지는 글(And, And, And)은 사실 나열이라 지루하고, "그런데"가 여러 번 나오는 글은 산만하다. 문단마다 But이 하나인지 확인하면 메시지가 선명해진다.

## SUCCESs: 기억에 남게 만드는 여섯 조건

Chip Heath와 Dan Heath가 『Made to Stick』에서 정리한 조건이다. 구조가 아니라 장 하나하나의 내용을 다듬을 때 쓴다.

| 조건 | 뜻 | 장표에 적용 |
| --- | --- | --- |
| Simple | 핵심 하나 | 한 장에 메시지 하나 |
| Unexpected | 예상을 깨는 지점 | "커넥션 풀을 늘렸더니 늘린 만큼 다 썼다" |
| Concrete | 구체적 수치와 장면 | "점수 차이" 대신 "157점 대 181점" |
| Credible | 믿을 근거 | 문서 링크, 테스트 조건 |
| Emotional | 듣는 사람의 이해관계 | 고객 결제 실패, 야간 장애 대응 |
| Stories | 사례와 이야기 | 다른 회사의 장애와 해결 과정 |

## 들려주고, 말하고, 다시 들려준다

교육 자료에서 오래 쓰인 구조다. 무엇을 말할지 먼저 알려 주고(목차, 개요), 본문을 말하고, 무엇을 말했는지 정리한다(요약, 복습). 처음 보는 내용이 많을수록 듣는 사람은 지금 어디쯤인지 알아야 따라온다. 목차를 섹션 구성과 맞추고, 섹션 끝에 그 섹션을 한 장으로 정리하는 장을 두면 된다.

## 상황별로 고르는 구조

| 상황 | 구조 | 이유 |
| --- | --- | --- |
| 경영진 보고, 의사결정 요청 | 피라미드(답 먼저) | 시간이 짧고 결론에 대한 판단이 목적 |
| 기술 세미나, 교육 | SCQA를 덱 전체에 펼침 | 문제를 겪어 봐야 원리와 답을 받아들임 |
| 새 방식 도입 제안, 키노트 | Sparkline | 현재 상태의 비용을 느끼게 해야 움직임 |
| 메일 첫 문단, 장표 리드 | ABT | 한 문장으로 맥락, 문제, 행동을 전달 |
| 모든 덱의 마무리 점검 | 수평·수직 논리, SUCCESs | 순서와 장별 내용을 검증 |

## 적용 기록: 34장 기술 덱 재배치

Kubernetes 스케줄러 원리와 노드 유지보수 절차를 설명하는 34장 덱이 있었다. 처음에는 원리부터 쌓아 올리는 순서였다.

| 처음 순서 | 문제 |
| --- | --- |
| 1. 스케줄러 내부 구조 | 왜 알아야 하는지 모른 채 원리를 듣는다 |
| 2. 점수 계산 상세 | 계산이 어디에 쓰이는지 연결되지 않는다 |
| 3. 노드 작업 시 고려 사항 | 앞의 원리를 기억해 다시 꺼내야 한다 |
| 4. 권장 작업 방법 | 답이 맨 끝에야 나온다 |

듣는 사람은 이 덱의 고객사 운영팀이었다. 원리를 이해시켜야 하므로 답을 맨 앞에 두는 피라미드보다 SCQA를 덱 전체에 펼치는 쪽을 골랐다.

| 바꾼 순서 | SCQA | 들어간 장 |
| --- | --- | --- |
| 1. 노드 작업 흐름과 문제 | S, C | 실제 작업서 흐름 영상, cordon 범위에 따라 Pod가 엉뚱한 노드로 가는 장면, 영역 분산 규칙으로 Pending이 되는 장면 |
| 2. 전체 구조와 drain 동작 | Q | API 서버 중심의 구성요소 역할, drain 시 API 호출 순서 |
| 3. 스케줄러 판단 로직 | Q | Filter와 Score, 실제 필드 값으로 본 계산, 섹션 끝 정리 영상 |
| 4. 권장 작업 방법 | A | 시나리오 비교, 작업 전 확인 사항, 권장 순서 |
| 5. 부록 | 근거 | 플러그인 가중치, 계산식, 배치 선택 수단 표 |

바꾸면서 같이 고친 것이 있다. 문제 장면을 앞으로 옮기니 그 장의 노트에 있던 "앞 장 계산과 같은 값" 같은 참조가 틀어졌다. 장을 옮길 때는 노트와 본문의 상호 참조를 장 번호가 아닌 장 제목으로 쓰면 이런 수정이 줄어든다. 고정된 상위 구조(전체 구조)를 세부 구조(스케줄러 내부)보다 앞에 둔 것도 같은 원칙이다. 전체 그림을 먼저 보여 주고 확대해 들어가야 세부가 어디에 붙는지 안다.
