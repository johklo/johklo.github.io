시험장에서 모든 책을 펼쳐 놓는 대신, 질문에 필요한 쪽을 찾아 옆에 두고 답한다고 생각해 보겠습니다. 필요한 쪽을 찾는 일이 검색, 그 쪽을 답변자에게 건네는 일이 문맥 구성, 읽고 답하는 일이 생성입니다. 세 단계 중 하나라도 틀리면 최종 답이 틀릴 수 있습니다.

이번에는 Chroma에 작은 여행 안내 세 개를 넣고, **찾은 문서와 모델의 답을 따로** 확인했습니다.

## 6.1 의미 검색

키워드 검색은 나타난 단어나 형태를 중요한 신호로 사용합니다. 의미 검색은 질문과 자료를 벡터로 표현해 유사한 내용을 찾습니다. “대중교통으로 이동하는 방법”과 “기차와 버스 이용 안내”처럼 단어가 달라도 관련 자료를 찾으려는 목적입니다.

의미가 비슷한 문서가 곧 정확한 답은 아닙니다. 다른 지역의 교통 정보나 예전 요금표도 질문과 비슷하게 보일 수 있습니다. 대상과 날짜 같은 조건을 별도로 확인해야 합니다.

### 6.1.1 문서 하나에 대한 질의응답

문서가 짧으면 질문과 문서 전체를 한 번의 프롬프트에 넣을 수 있습니다. “제공한 문서 안에서 답하고 근거가 없으면 모른다고 답한다”는 규칙을 두는 기본 구조입니다.

이 경우에도 답이 문서에 실제로 있는지 검사해야 합니다. 모델이 지침을 받았다고 환각이 완전히 사라지지는 않습니다. 후속 질문에 답하려면 이전 대화도 필요한 범위만큼 제공해야 합니다.

### 6.1.2 지식베이스에 대한 질의응답

문서 수와 길이가 늘어나면 모든 내용을 매 요청에 넣기 어렵습니다. 새 문서가 추가되거나 접근 범위가 달라지는 문제도 생깁니다.

사용자는 질문만 보내더라도 프로그램은 어떤 저장소에서 어떤 문서를 가져올지 알아야 합니다. 모델 API를 호출했다는 사실만으로 사내 파일과 데이터베이스가 자동 연결되는 것은 아닙니다.

### 6.1.3 RAG 패턴

Retrieval은 근거를 찾는 단계, Augmentation은 그 근거를 질문과 함께 입력에 넣는 단계, Generation은 그 입력으로 답을 만드는 단계입니다.

자료 준비는 질문마다 반복할 필요가 없습니다. 파일을 읽고 청크로 나눈 뒤 임베딩과 원문을 저장하는 과정을 인덱싱 또는 ingestion이라고 부릅니다.

![파일과 인트라넷 및 위키의 자료를 추출하고 청크로 분할한 뒤 임베딩과 원문을 벡터 데이터베이스에 적재하는 RAG 준비 과정.](/images/ai-agents-and-applications/figure-6-03.png "그림 6.3. RAG의 자료 적재 과정. 출처: AI Agents and Applications, 6장.")

왼쪽의 원본 형식은 달라도 분할 뒤에는 공통 검색 단위가 됩니다. 중요한 점은 오른쪽 저장소에 임베딩만이 아니라 나중에 생성 모델이 읽을 원문과 출처도 연결되어야 한다는 것입니다. 벡터는 검색을 위한 표현이며 최종 답의 근거 자체를 대신하지 않습니다.

질문이 들어오면 질문을 임베딩하고 저장된 청크와 비교합니다. 찾은 청크의 원문을 프롬프트에 넣고 생성 모델을 호출합니다. 인덱스가 갱신되지 않으면 모델에 새 문서를 넣었다고 생각해도 실제 검색에는 반영되지 않을 수 있습니다.

## 6.2 벡터 저장소

### 6.2.1 무엇을 저장하는가

임베딩은 텍스트나 이미지의 특성을 숫자 목록으로 표현한 벡터입니다. 벡터 저장소는 이런 표현을 보관하고 가까운 벡터를 찾는 기능을 제공합니다.

일반적인 기록에는 청크 ID, 임베딩, 원문, 메타데이터가 필요합니다. 저장소가 모든 항목을 직접 보관하지 않는다면 원문 저장소와 식별자로 연결해야 합니다.

벡터의 각 차원을 사람이 읽을 수 있는 주제 이름처럼 해석하는 것은 적절하지 않습니다. 모델이 만든 표현 공간 안에서 상대적인 거리를 이용하는 것입니다.

### 6.2.2 유사도와 검색

질문 벡터와 문서 벡터 사이의 거리를 계산해 가까운 후보를 고릅니다. 유클리드 거리는 위치의 차이, 코사인 유사도는 주로 방향의 유사성을 비교합니다. 어떤 척도가 적합한지는 임베딩 모델과 저장소 설정에 따릅니다.

전체 벡터를 매번 비교하면 자료가 많을 때 비용이 커집니다. 근사 최근접 이웃 검색인 ANN은 속도를 위해 정확한 이웃을 일부 놓칠 수 있는 검색 방식입니다. 검색 품질에는 임베딩뿐 아니라 인덱스와 검색 설정도 영향을 줍니다.

같은 차원의 벡터라고 모두 비교 가능한 것은 아닙니다. 서로 다른 모델이 만든 벡터는 같은 의미 공간이라는 보장이 없습니다. 문서 임베딩과 질문 임베딩은 호환되는 모델과 설정으로 생성해야 합니다.

### 숫자로 보는 “가까운 문서”

지도의 두 지점 사이 거리를 재는 것처럼 생각해 보겠습니다. 실제 문장 임베딩은 훨씬 많은 차원을 쓰지만, 계산 원리는 작은 벡터로 볼 수 있습니다.

```text
질문 q = (1, 0)
문서 A = (0.9, 0.1)
문서 B = (0, 1)

유클리드 거리:
  q와 A = sqrt((1 - 0.9)^2 + (0 - 0.1)^2) ≈ 0.141
  q와 B = sqrt((1 - 0)^2 + (0 - 1)^2) ≈ 1.414

코사인 유사도:
  dot(q, A) / (norm(q) × norm(A)) ≈ 0.994
  dot(q, B) / (norm(q) × norm(B)) = 0
```

이 예시에서는 A가 더 가깝습니다. 하지만 거리의 숫자가 “정답일 확률 99.4%”라는 뜻은 아닙니다. 임베딩 공간에서 두 표현이 비슷하다는 신호일 뿐입니다. 비슷한 기차 안내문이라도 다른 도시나 다른 연도의 자료일 수 있습니다.

또 저장소가 코사인 **거리**를 반환하면 코사인 유사도와 점수 방향이 달라질 수 있습니다. 예제 결과의 `distances`를 정확도 백분율처럼 표시하지 않고, 사용한 컬렉션의 척도와 반환 규칙부터 확인해야 합니다.

### 6.2.3 라이브러리와 데이터베이스

벡터 검색 라이브러리는 검색 인덱스 구현에 집중할 수 있습니다. 데이터베이스는 여기에 원문과 메타데이터, 갱신과 영속화, 접근과 운영 기능을 결합합니다.

다만 특정 라이브러리는 무조건 읽기 전용이고 특정 DB는 모든 운영 기능을 제공한다는 식으로 일반화할 수는 없습니다. 구현과 버전마다 범위가 다릅니다. 필요한 기능을 각각 확인해야 합니다.

| 확인 항목 | 이유 |
| --- | --- |
| 원문과 메타데이터 보관 | 검색 결과를 답의 근거로 복원 |
| 필터와 식별자 | 문서 범위와 사용자 접근 조건 적용 |
| 추가와 갱신, 삭제 | 최신 자료와 원천 문서 변경 반영 |
| 재시작 후 보존 | 메모리 실험과 운영 저장의 구분 |
| 동시 접근과 운영 | 처리량과 백업, 권한의 요구 충족 |

### 6.2.4 저장소 선택

FAISS 같은 검색 라이브러리, Chroma와 전용 벡터 DB, PostgreSQL의 pgvector처럼 기존 DB에 벡터를 넣는 방식이 있습니다.

선택의 출발점은 데이터 규모뿐 아니라 기존 저장소와의 연결, 필터 요구, 변경 빈도와 운영 역량입니다. 검색 속도만 비교하고 삭제와 백업, 문서 권한을 빼면 실제 서비스 요구와 어긋날 수 있습니다.

### 6.2.5 Chroma에 저장하고 검색하기

책은 Chroma 컬렉션에 문서와 ID를 넣고 질의합니다. 컬렉션은 관련 기록을 묶는 단위입니다. 문서를 추가할 때 임베딩을 직접 전달하거나 설정한 임베딩 함수가 만들도록 할 수 있습니다.

메모리 클라이언트와 영속 클라이언트는 수명이 다릅니다. 메모리에서 정상 검색됐다고 프로세스 재시작 뒤에도 자료가 남는 것은 아닙니다.

검색 결과는 여러 질의를 지원하기 위해 중첩 목록 형태일 수 있습니다. 첫 질의의 문서와 ID, 거리 결과를 올바르게 대응시켜야 합니다. 거리인지 정규화된 관련도 점수인지도 확인해야 하며 높은 값이 항상 더 좋은 것은 아닙니다.

`k` 또는 반환 개수는 근거의 양을 정합니다. 너무 작으면 필요한 부분을 놓치고, 너무 크면 잡음과 토큰이 늘어납니다. 상위 결과는 관련 자료가 없어도 반환될 수 있으므로 개수만으로 충분함을 판단하면 안 됩니다.

### Chroma의 중첩 결과에서 한 행 복원하기

여러 질문을 한 번에 보낼 수 있기 때문에 결과의 바깥 목록은 질문, 안쪽 목록은 그 질문의 검색 순위입니다. 아래는 구조를 설명하기 위한 가상 결과입니다.

```json
{
  "ids": [["rail", "bus"]],
  "documents": [["기차 안내 본문", "버스 안내 본문"]],
  "metadatas": [[{"source": "rail"}, {"source": "bus"}]],
  "distances": [[0.2, 0.7]]
}
```

첫 질문의 첫 후보를 읽을 때는 네 필드 모두 `[0][0]`으로 대응시켜야 합니다. ID는 `rail`인데 본문은 `[0][1]`의 버스 설명을 붙이면, 검색 자체는 맞아도 잘못된 인용이 됩니다. 첫 인덱스는 질문 번호, 둘째는 같은 검색 결과 안의 위치라고 구분하면 쉽습니다.

`n_results=1`은 이 안쪽 목록의 최대 후보 수를 정합니다. 저장소에 요금 자료가 하나도 없는데 요금을 물어도 가장 가까운 기차 안내가 나올 수 있습니다. 따라서 “후보가 반환됨”과 “필요한 사실이 들어 있음” 사이에는 별도의 근거 확인이 필요합니다.

## 6.3 RAG 직접 구현

![질문을 임베딩해 벡터 DB에서 관련 원문 청크를 찾고, 원래 질문과 청크로 만든 프롬프트를 LLM에 보내 답을 생성하는 RAG 질의응답.](/images/ai-agents-and-applications/figure-6-04.png "그림 6.4. RAG의 검색과 생성 단계. 출처: AI Agents and Applications, 6장.")

앞의 그림 6.3이 도서관에 책을 정리하는 과정이었다면, 이 그림은 질문을 받은 사서가 자료를 찾아 답변자에게 건네는 과정입니다. 왼쪽 검색은 **질문 벡터로 후보를 찾는 일**, 오른쪽 생성은 **검색된 원문을 읽는 일**입니다. LLM으로 올라가는 프롬프트에 원래 질문도 함께 들어가는지 확인하면 두 단계의 경계를 놓치지 않습니다.

### 6.3.1 자료 검색

질문을 검색 함수에 넣고 관련 청크의 본문을 받습니다. 이때부터 최종 답을 생성할 필요는 없습니다. 먼저 찾은 자료가 질문에 필요한 사실을 포함하는지 직접 볼 수 있어야 합니다.

다른 지역이나 다른 버전의 자료가 검색되었다면 원문 메타데이터와 인덱싱, 질문 표현을 확인합니다. 검색이 틀린 상태에서 생성 프롬프트만 바꾸면 원인을 놓치기 쉽습니다.

### 6.3.2 생성 모델 호출

사용자 질문과 검색한 문맥, 응답 규칙을 조합합니다. 모델이 읽는 것은 일반적으로 검색된 텍스트이지 벡터 숫자가 아닙니다.

원문이 부족하면 모른다고 답하도록 하고, 사실과 출처를 연결합니다. 그러나 문서가 외부에서 왔다면 그 안의 지시를 실행하지 않도록 신뢰 경계를 유지해야 합니다. RAG는 외부 텍스트를 모델 입력에 추가하기 때문에 입력의 정확성과 안전성이 모두 중요합니다.

### 6.3.3 챗봇 조합

기본 조합은 다음과 같습니다.

```text
사용자 질문
  → 질문 임베딩
  → 검색과 원문 조회
  → 질문과 문맥으로 프롬프트 구성
  → 생성 모델 호출
  → 응답과 출처 반환
```

이 구조가 한 질문에 답한다고 대화 메모리가 생기는 것은 아닙니다. 이전 질문에서 가리킨 장소나 대상은 다음 요청에 별도로 전달해야 합니다. 다음 장은 그 연결을 다룹니다.

### 6.3.4 용어 정리

| 용어 | 의미 |
| --- | --- |
| 문서 | 본문과 메타데이터를 가진 원천 단위 |
| 청크 | 검색이나 처리에 사용할 문서 조각 |
| 임베딩 | 자료와 질문의 유사도 비교를 위한 벡터 표현 |
| 인덱싱 | 검색 가능한 자료를 준비하고 저장하는 과정 |
| 검색기 | 질문에 맞는 문서 후보를 반환하는 구성 요소 |
| 문맥 | 최종 생성에 실제로 전달한 근거와 배경 |
| 생성 | 문맥과 지침으로 답변을 작성하는 과정 |

검색 자료, 실제 문맥, 최종 답을 따로 기록하면 실패를 나눠 볼 수 있습니다. 자료를 찾았지만 길이 제한으로 문맥에서 빠질 수 있고, 문맥에 있어도 생성 모델이 잘못 해석할 수 있습니다.

### 같은 오답을 세 위치로 나누어 진단하기

질문은 기차 운행 간격이고 정답 근거는 `rail` 문서라고 해 보겠습니다.

| 관찰 | 실패 위치 | 먼저 확인할 것 |
| --- | --- | --- |
| 검색 결과에 박물관만 있음 | Retrieval | 임베딩 입력, 자료 분할, 필터, 후보 수 |
| rail을 찾았지만 프롬프트에는 박물관 본문을 넣음 | Augmentation | 결과 인덱스 대응과 문맥 조립 |
| 프롬프트에 30분이 있는데 답은 15분 | Generation | 모델의 근거 사용, 지침과 답 검증 |

이 세 상황을 모두 “RAG가 안 된다”라고 부르면 모델·청크 크기·검색 개수를 한꺼번에 바꾸기 쉽습니다. 그러면 무엇이 효과가 있었는지 알기 어렵습니다. 검색 결과를 먼저 고정하고 문맥 조립을 검사한 뒤 생성 결과를 비교하는 순서가 유용합니다.

평가 질문도 정답이 있는 경우만 넣지 않습니다. 운행 간격은 문서에 있지만 요금은 없는 데이터라면, 두 질문이 각각 “정확한 답”과 “근거 부족”을 평가합니다. 모르는 질문에서 답을 만들어 내지 않는 능력은 필요한 자료를 찾는 능력과 별도로 확인해야 합니다.

## 직접 해보기: 문서 세 개로 RAG 만들기

`ch06.py`로 저장합니다. Chroma 기본 임베딩 함수는 첫 실행 때 공개 `all-MiniLM-L6-v2` 모델을 내려받습니다. 아래 안내문은 실습용 데이터이며 현재 여행 정보가 아닙니다.

```python
import chromadb
from chromadb.config import Settings
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_ollama import ChatOllama

client = chromadb.PersistentClient(
    path="rag-study", settings=Settings(anonymized_telemetry=False),
)
collection = client.get_or_create_collection("travel-study")
collection.upsert(
    ids=["rail", "bus", "museum"],
    documents=[
        "The study train from Truro to Falmouth runs every 30 minutes.",
        "The study bus to Perranporth leaves Truro at 09:00.",
        "The study museum in Truro opens at 10:00.",
    ],
    metadatas=[{"source": name} for name in ("rail", "bus", "museum")],
)
question = "How often does the railway service to Falmouth depart?"
found = collection.query(query_texts=[question], n_results=1)
ids = found["ids"][0]
documents = found["documents"][0]
print("Retrieved:", ids, documents)
assert ids == ["rail"], "The expected source was not retrieved"
prompt = ChatPromptTemplate.from_template(
    "Answer only from these study notes. Cite the supplied source ID. "
    "If the notes do not answer the question, say you do not know.\n"
    "Source: {source}\nNotes: {context}\nQuestion: {question}"
)
chain = prompt | ChatOllama(
    model="llama3.2:latest", temperature=0, num_predict=130,
) | StrOutputParser()
print("Answer:", chain.invoke({
    "source": ids[0], "context": documents[0], "question": question,
}))
print("Stored documents:", collection.count())
```

```powershell
python ch06.py
```

질문에는 `railway service`라고 썼지만 검색 결과는 `rail` 안내문이었고, 답에는 `30 minutes`와 출처 `rail`이 포함됐습니다. 먼저 근거 적중을 확인하고 그다음 답변의 값이 원문과 일치하는지 비교했습니다.

같은 ID로 `upsert()`하므로 다시 실행해도 문서 수는 3개입니다. 매번 새 ID를 만드는 `add()` 방식과 달리, 이 예제는 같은 기록을 갱신합니다. 단, 원문에서 삭제된 ID를 자동으로 지우지는 않습니다.

### 실습이 인덱싱과 질의 단계를 나누는 지점

`upsert()`까지는 자료를 준비하는 작업입니다. `collection.query()`부터는 질문 한 건을 처리합니다. 운영에서는 인덱싱을 별도 작업으로 실행하고, 질문 경로는 준비된 컬렉션을 조회하는 식으로 분리할 수 있습니다. 원문이 바뀔 때만 해당 ID의 본문과 임베딩을 갱신하면 매 질문마다 같은 자료를 다시 계산하지 않아도 됩니다.

질의 뒤의 `assert ids == ["rail"]`은 이 작은 데이터셋의 기대 근거를 검사합니다. 그 이후 모델에는 벡터가 아니라 `documents[0]`의 원문과 `ids[0]`의 출처가 전달됩니다. 두 단계를 따로 보므로 검색이 잘못됐을 때 생성 답변의 문체를 고치는 식의 우회를 피할 수 있습니다.

영속 경로 `rag-study`를 유지한 채 자료 목록을 바꾸면 이전 ID가 남을 수 있습니다. `upsert()`는 입력한 ID를 추가·갱신하는 연산이지 컬렉션 전체를 현재 목록과 동기화하는 명령은 아닙니다. 삭제할 문서의 ID도 관리해야 “최신 자료만 검색한다”는 요구를 지킬 수 있습니다.

직접 확인할 질문: “가장 가까운 문서가 있으니 답도 반드시 있을까요?” 저장소는 관련성이 낮아도 상위 후보를 돌려줄 수 있습니다. `n_results=1`은 정답의 개수가 아니라 **받을 후보 수**입니다.

실패 실험: 질문을 “What is the train fare?”로 바꾸면 기차 문서는 찾더라도 요금 근거는 없습니다. 답변이 요금을 만들어 내는지와 모른다고 답하는지를 따로 검토합니다.

한 줄 정리: RAG는 **검색된 원문·생성에 넣은 문맥·최종 답**을 분리해서 확인해야 개선할 수 있습니다.

## 질문

### 운행 간격은 찾았는데 요금 질문에는 왜 답하면 안 될까요?

검색 결과의 문서 주제는 맞아도 질문에 필요한 값이 없기 때문입니다. “가장 가까운 기차 문서”라는 사실은 “요금 근거가 있는 문서”와 다릅니다. 원문에 요금이 있는지부터 확인하고 없으면 부족함을 반환해야 합니다.

이 경우 `n_results`를 늘려 해결될지, 데이터에 요금표 자체가 없는지 나눠 봅니다. 없는 자료를 찾는 문제와 있는 자료를 놓친 문제는 다른 개선이 필요합니다.

### 자료를 많이 검색하면 환각이 사라질까?

관련 없는 자료와 모순된 자료가 늘 수 있습니다. 근거의 관련성과 충분함, 답이 근거를 따르는지를 따로 확인해야 합니다.

### 임베딩 모델을 바꾸고 기존 인덱스를 계속 써도 될까?

차원이 같아도 표현 공간이 다를 수 있습니다. 기존 문서와 새 질문의 벡터 호환성을 확인하고 필요하면 전체를 다시 임베딩해야 합니다.
